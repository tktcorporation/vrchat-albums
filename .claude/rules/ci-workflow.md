# CI / PR ワークフロー

push 前に CI をローカルで再現し、push 後は全チェックが pass するまで見届ける。どちらも「たぶん大丈夫」で飛ばさない。

## セルフレビューの往復では push をまとめる

自分でレビューと修正を繰り返している間は、ラウンドごとに push せず、収束してから push する。途中のラウンドの CI 結果は次の修正で上書きされるので、実行枠と待ち時間を使うだけで終わる。PR を既に出していても同じ。

PR 作成後の追加コミットでセルフレビューを回すかどうかは、`pr-self-review.md` の節 `既存 PR への追加コミットでは「指摘は外部レビューが見つけてくれる」に頼らない` が決める。

レビューで指摘を受けた後は、`.claude/rules/pr-self-review.md` の「既存 PR への追加コミット」の手順を優先する。局所修正をすぐ push すると、CI と外部レビューが修正のたびに走る。CI が赤いなど、レビュー指摘とは別の緊急対応は、原因を確認して必要な修正をまとめて push する。

この節が決めるのは、セルフレビューを回すと決めた場合の push のタイミングだけで、そもそも push してよいかは別の判断になる。依頼の範囲に入っているか、手元から失われる前に残す必要があるか、といった事情はそれぞれの場面のルールが決める。

未コミットの変更や未 push のコミットを検知して push を促す仕組み（停止時の hook やリマインダー）があっても、促されたことだけを理由に push しない。促しが求めているのは変更を失わないことなので、それがコミットで足りるならコミットで止める。セルフレビューのループ中はこの促しが毎ラウンド届く。それを理由には push せず、push は収束後の 1 回にまとめる。

## push 前: CI をローカルで再現する

1. `.github/workflows/` の全ワークフローを読み、`push` / `pull_request` トリガーで走る `run:` コマンドをすべて列挙する
2. そのうちローカルで実行できるものを特定する
3. 全部実行する。1 つでも fail したら修正して再実行する
4. 全 pass を確認してから push する

ローカルで実行しなくてよいのは次だけで、これ以外は省略しない。

- CI 固有の secret / 環境変数が必要なコマンド（エラー監視サービスへの upload 等）
- GitHub API 操作（PR コメント投稿、ラベル付与）
- E2E テスト（明示的に求められたときだけ実行する）
- Docker や CI 固有環境でしか動かないコマンド

典型的な対象は lint・format・型チェック・test・未使用コード検出・ライセンスチェック・ビルド・changeset の有無。生成物と SSOT の乖離検知のようなプロジェクト固有のチェックがワークフローにあれば、それも実行する。

## push 後: CI が pass するまで見届ける

1. `gh pr checks <PR番号> --watch` で全チェック pass まで監視する
2. fail したら `gh run view <run-id> --log-failed` でログを読み、原因を特定する
3. 修正して push し、再度監視する
4. 全チェックが pass するまでこのサイクルを回す

`gh pr checks` は内部で GraphQL を使うので、GraphQL を拒否して REST だけを通す環境では失敗する。その環境では同じ情報を REST で読む。head の SHA は `git ls-remote origin refs/heads/<branch>` で取る。

| 知りたいこと                          | REST の呼び出し                                                                                              |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| チェック（GitHub Actions など）の状態 | `gh api --paginate repos/<owner>/<repo>/commits/<sha>/check-runs --jq '.check_runs[] \| {name, status, conclusion}'`    |
| 外部 CI がコミットに付けた状態        | `gh api --paginate repos/<owner>/<repo>/commits/<sha>/status --jq '.statuses[] \| {context, state}'`                    |
| 失敗したジョブのログ                  | `gh api repos/<owner>/<repo>/actions/jobs/<job-id>/logs`（job-id は check-run の `details_url` の末尾の数字） |

`--watch` の代わりに、間隔を空けて読み直す（1 分未満の間隔で叩かない）。環境で何が使えるかは `bun "$CLAUDE_PROJECT_DIR"/.claude/hooks/github-doctor.ts` で確かめる。この診断は gh の有無と認証、REST と GraphQL のどちらが通るか、push のゲートが通るか、PR をどの経路で作るべきかを示し、何も書き換えない。

**全チェックが pass するまでユーザーに「完了」と報告しない。**

失敗が自分の変更と無関係だと判断したときは、その根拠（base branch でも再現する / ローカルで再現しない / 失敗箇所が差分に触れていない）を示す。根拠なしに flake と断定しない。

## push 後: レビューコメントに対応する

自動レビュー（bot）や人のコメントは、push から数分遅れて届く。CI が緑になっても、未解決のレビュースレッドが残っているうちは完了ではない。

1. bot のレビューが設定されているリポジトリでは、push 後に数分待ってからコメントを取りに行く（待つ間は別の作業を進める。1 分未満の間隔で叩かない）
2. 指摘が届いたら、レビューを始める前に、PR のブランチをチェックアウトしたディレクトリで `bun "$CLAUDE_PROJECT_DIR"/.claude/hooks/observe-pr-feedback.ts` を実行し、観測時点のラウンド数を記録する（Stop フックが新しいスレッドを知らせた場合は自動でも記録する）。件数にかかわらず差分全体のセルフレビューを再開する。観測後に 2 ラウンド以上（最後は codex review）を記録して収束するまで修正を push しない。コメントごとに「修正 / 直さない理由 / 回答」を判断し、対応したスレッドを resolve する。既存スレッドへの返信も Stop フックが知らせるので、LLM が内容を読み、新たな指摘なら同じ手順を行う
3. ローカルで収束した修正をまとめて 1 回 push し、1 に戻る。同じ PR で異なる HEAD に対する外部指摘が 3 回目になったら、次の修正と push を止める。各 HEAD で届いた指摘とローカルレビューで見逃した理由を原因ごとにまとめ、**なぜレビューが続くのか**を診断する。同じ欠陥が形を変えて出ているのか、修正で別の欠陥を作っているのか、要件やレビュー範囲が過剰なのかを見分ける。契約や責務を変える案、要件や対象範囲を見直す案などを効果・影響・追加の CI とレビューのコストで比較し、推奨案を添えてユーザーに**採る方針**を尋ねる。「もう一度レビューするか」だけを聞かない。答えを得たら、同じディレクトリで `bun "$CLAUDE_PROJECT_DIR"/.claude/hooks/record-pr-feedback.ts asked "<診断とユーザーが選んだ方針>"` を実行して記録し、その方針で実装とローカルレビューを収束させてから push する

記録用のスクリプトは実行したディレクトリのチェックアウトを対象にする（サブモジュールや worktree の PR ならその中で実行する）。`$CLAUDE_PROJECT_DIR` はルートプロジェクトのディレクトリで、設定されていない環境ではルートプロジェクトの絶対パスに置き換える。

Stop フック（`.claude/hooks/stop-pr-comments.ts`）が未対応スレッドを知らせる。Stop フックが見るのはセッションの現在地のチェックアウトの PR だけで、コマンドごとに `cd` してサブモジュールで作業しているとその PR は知らせない。外部指摘の観測履歴は指摘を読んだ時点、push 前のゲート、相談記録時に共通の処理で更新し、ユーザーが選んだ方針は `record-pr-feedback.ts` が記録する。通常の Bash の直接 `git push` では、`git -C` や `cd` で移った先の push 元チェックアウトについて、PreToolUse フックが GitHub の新規インラインコメントと変更要求レビュー本文を確認し、同じ PR で異なる HEAD への指摘が規定回数に達していればユーザー判断の記録を要求する。初回の指摘から、指摘後に追加したローカルレビューのラウンドが収束するまでは push を止める。同じ HEAD への複数コメントは相談の回数では 1 回と数える。通常のコメント付きレビューを対象にする簡易ガードで、短い返信や一般コメントの指摘性は機械的に確定しない。フックは特殊な refspec やリモート設定も完全には解析しない。LLM は送信先を確認し、別の経路で push するときも同じ手順を守る。

この push のゲートは、基本の経路（origin の、いま作業しているブランチの PR）で外部指摘に気付き、セルフレビューへ戻るための緩いガードレールである。gh が無い・認証できない・アクセスを拒否される・通信できない・origin から対象を決められないなどで PR を確かめられないときは、push を止めずに通し、確かめられなかった内容と `github-doctor.ts` で確かめる手順を警告として示す。fork からの PR、SSH の Host 別名を使う origin、origin 以外のリモートへの push、refspec でのブランチ名の変更、同じ head からの複数の PR といったまれな構成は対象外で、それらを塞ぐためにゲートの設計を広げない。

`gh` が認証できないクラウドでは、指摘を読んだ直後に `.claude/guides/tools/cloud-review.md` の GitHub コネクタ用ラッパーを `observe` モードで実行する。観測後の 2 ラウンドを記録したら、同じラッパーの `push` モードで指摘を再取得してゲートを通す。直接の `git push` に置き換えない。

## changeset

changeset を使うプロジェクトでは、その CI が何を要求するかを確認して従う。全 PR に新規の `.changeset/*.md` を要求する CI なら、ドキュメントのみ・リファクタなど版に影響しない変更でも、frontmatter を空にしたファイルを追加して bump 無しを表明する。要求しない CI なら、版に影響する変更のときだけ追加する。bump するパッケージ名は `package.json` の `name` を参照する。

確認先は「変更を出す先のリポジトリ」の CI 設定になる。サブモジュールや別リポジトリで作業しているときは、手元のワークスペース直下の `.github/workflows/` を見てもその要求は分からない。

## 禁止事項

- CI チェックを通さずに push する
- lint エラーを disable コメントで安易に抑制する（正当な理由がある場合は理由を明記する）
- テスト失敗を無視して push する
- 「たぶん大丈夫」で push する（実行して確認する）
- レビューの指摘や CI の失敗への対応を、手元にためる
