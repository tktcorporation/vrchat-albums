# PR 作成前のセルフレビュー必須ルール

## 背景

Claude が作成した PR は、作成直後にセルフレビューを回すとほぼ確実に修正すべき問題が見つかる。1 回の指摘を直すと次のレビューで別の指摘が出ることが多く、回数を固定したレビューでは収束しない。指摘が出なくなるまで回す。

## 仕組み

`gh pr create` は PreToolUse フック（`.claude/hooks/require-pr-self-review.ts`）でブロックされる。フックはラウンドごとの記録を読み、「2 ラウンド以上あり、最後のラウンドが codex review・現在の HEAD に対するもの・かつ指摘 0 件かユーザーが受け入れた（`accepted`）」のときだけ通す。最後を codex review 以外にしても通らない（それより前の codex ラウンドは古いコミットしか見ていない可能性があるため）。指摘の残るラウンドを、受け入れの記録なしに何回重ねても通らず、収束後に新しいコミットを重ねると、その HEAD に対する codex review をもう一度要求される。

このゲートは対象を作業ツリーの現在のブランチで判定する。`gh pr create --head <branch>` で別ブランチを PR にする場合は、そのブランチのディレクトリ（worktree）でレビュー・記録してから作成する。**hook はコマンド文字列から `--head` の指定先を読み取らない**（`--title`/`--body` の自由記述に `--head` という文字列が現れるとゲートを誤って通してしまうため、あえて実装していない）。したがって、レビュー済みブランチのディレクトリにいながら `--head` で別の未レビューブランチを指定すれば、この防御は効かない。この経路は仕組みで防いでおらず、`agent-work-discipline.md` が禁じる行為（名指しされた対象をすり替える）に該当する運用上の禁止事項として扱う。

## 手順

PR を作成したいとき、以下を自動的に実行する:

### 0. plan / spec 消費チェック

変更が `docs/plans/` `docs/superpowers/plans/` `docs/superpowers/specs/` の設計を実装するものか確認し、消費してよいかを `doc-placement.md` の寿命の節の手順で判断する。このステップは hook による強制対象外なので、都度手動で確認する。フォローアップ TODO が残るという理由で plan / spec を残したまま PR を作成した場合、以後そのままの PR に追加コミットで残タスクを終わらせることがある。マージ前にこのチェックを再実行し、消費できる状態になっていないか確認する。

### 1. レビューと修正を収束まで繰り返す

`.claude/skills/pr-review-loop/SKILL.md` の手順で回す。1 ラウンドは「差分をレビューする → 指摘全体を根本原因でまとめる → 直す」。指摘が 0 件になったラウンドは収束、指摘の根本原因が前ラウンドから変わらなくなったラウンドは途中収束で、`gh pr create` を通すにはどちらも上の「仕組み」節の条件（`accepted` を含む）を満たす必要がある。

レビュアーはラウンドごとに選ぶ。`pr-deep-review` の手順で動くサブエージェントを基本にし、収束させる最後のラウンドは `codex review --base <default-branch>`（`codex-pairing.md`）で行う（条件は上の「仕組み」節を参照）。`codex review` が使えない環境では code-reviewer 系のサブエージェントで代える（記録時の `codex` タグは、このラウンドが実際の `codex review` かその代替であることを示す。同一モデル・同一手順で回した通常のラウンドには付けない）。

`codex` タグは記録するエージェント自身の申告であり、hook はそれが実際に codex review によるものかを検証できない。虚偽の記録は `agent-work-discipline.md` が禁じるツール結果の捏造にあたる。

### 2. ラウンドごとに記録する

ラウンドの指摘に対応し終えるたびに、そのラウンドの指摘件数を添えて記録する。指摘が 0 件だったラウンドは 0 を渡す（それが収束の証拠になる）。そのラウンドが `codex review` によるものなら `codex` を渡す。途中収束をユーザーが受け入れたラウンドは `accepted` も渡す（このときも件数は実際のまま。0 だと偽らない）。

```bash
bun .claude/hooks/record-pr-review.ts <指摘件数> [codex] [accepted]
```

対応していない指摘があるラウンドは記録しない。件数は「レビュアーが挙げた件数」で、直さないと決めた指摘も含める。

一定のラウンドごとに振り返りが必要になり、済ませるまで、収束しないラウンドを記録できない。振り返りでは、指摘件数が下がっていても、指摘の中身を分類し、レビューが続く原因と別の解決策を確認して診断メモに記録する。指摘件数が最良値を更新していない停滞、またはレビューの長期化では、全ラウンドの共通原因と設計・要件・進め方の案を比較し、ユーザーと採る方針を決めて `asked` を記録する。停滞していない定期的な振り返りでは `continue` または `replan` を選べる。間隔と閾値は `.claude/hooks/review-policy.ts` が定め、手順は `pr-review-loop` の「振り返り」にある。

```bash
bun .claude/hooks/record-pr-review.ts checkpoint <continue|replan|asked> "<診断メモ>"
```

`asked` も `codex` と同じく自己申告で、hook はユーザーへ確認したかを検証できない。

### 3. PR 作成

2 ラウンド以上・最後が codex review で現在の HEAD に対して 0 件になっていれば `gh pr create` が通る。途中収束（直しても指摘の根本原因が変わらない）は自分では閉じない。残る指摘と直さない理由をユーザーに示し、ユーザーが残りを受け入れたときだけ、その判断を PR 本文に書いて、現在の HEAD に対する codex review のラウンドを実際の指摘件数のまま `accepted` を付けて記録する（0 件だったと偽らない）。

## レビュー指摘への対応方針

**見つけたものは全て報告する。「問題ありませんでした」で済ませない。**

レビューで完全に問題がないことはほぼありえない。軽微なものでも見つけた事実を報告し、修正するか・あえてしないかを判断と理由付きで伝える。

| 重要度           | 対応                                                                           |
| ---------------- | ------------------------------------------------------------------------------ |
| Critical / Major | 即座に修正                                                                     |
| Minor            | 積極的に修正する。あえて修正しない場合は理由を明記して報告                     |
| Suggestion       | 修正するか、「こういうのを見つけたが、〇〇の理由で今回は修正しなかった」と報告 |

### 報告フォーマット

修正した指摘だけでなく、あえて修正しなかったものも含めて報告する:

```
## レビュー結果
### 修正した指摘
- [内容と修正内容]

### 見つけたが修正しなかったもの
- [内容] — 修正しなかった理由: [理由]
```

### アンチパターン

- 「特に問題ありませんでした」とだけ報告する → 何を見て何を判断したか不明
- 軽微な指摘を黙って無視する → 見つけた事実自体を報告する
- 全部直して報告にだけ「問題なし」と書く → 何を直したかも書く

### 指摘が同じ根本原因を指して振動したら打ち切る

複数ラウンドのレビューでは、命名や共通化のような指摘が、ラウンドごとに違う解決策を提案しながら再発することがある。指す先が同じ根本原因（例:「薄い try-catch をヘルパーに切り出すべきか」）なら、往復のたびに採用・却下を繰り返さず、一度判断したら理由とともに固定し、以後の同種指摘は「検討済み」として打ち切る。

## 注意

- ラウンドの記録はブランチごとに、主チェックアウトの `.git/claude/pr-review/<ブランチ名>.rounds` に置く（`.claude/hooks/review-count.ts`）。worktree から記録しても hook と同じファイルになり、別ブランチの記録とは混ざらない
- 記録のリセットは `.claude/hooks/reset-pr-review-count.ts`（PostToolUse）が行う。`post-bash-pr.ts` はコマンドの終了コードではなく、`gh pr view` でそのブランチに実際に PR が存在するかを確認してから発火する（終了コードは `|| true` 等で上書きできるため信用しない）

## 既存 PR への追加コミットでは「指摘は外部レビューが見つけてくれる」に頼らない

このルールが強制されるのは `gh pr create` の瞬間だけだが、避けたい振る舞いは PR 作成後に積む追加コミットにもそのまま当てはまる。**push した変更に、外部のレビュー（`codex review` や CI）から指摘が来るだろうと自分で予測できているなら、その予測が立った時点で、push する前に自分のレビューループを回して収束させる。** 「とりあえず push すれば `codex review` が拾ってくれる」という考え方で、予測できている問題を外部レビューに投げない。

外部レビューへ先に push して指摘を待つと、レビューサービスの利用枠・CI の実行時間・往復の時間を同時に浪費する。

これは push のたびに機械的にレビューループを挟めという話ではない。自明に安全な変更（typo 修正、コメントの言い換え、既にレビュー済みの内容の再掲など）にまで律儀にループを回す必要は無い。判断が要るのは「この差分は指摘されそうか」という見立てで、見立てが立たない・自信が無いときは、外部レビューに委ねてよい。見立てが立っているのに投げるのをやめる、というのがこの節の対象。

`gh pr create` と違って、指摘を予測できているかは hook で判定できないので、都度自分で判断する。指摘を予測して自分のレビューループへ回すときの手順は、PR 作成前のループと同じ（各ラウンドはサブエージェントでレビューし、収束させる最後のラウンドは `codex review` で行う）。push 後に届いた指摘が、予測できたはずなのに見送ったものだったら、次からはその種の変更を予測対象に加える。

**GitHub 上で実際にレビュー指摘が届いた場合は、予測の有無にかかわらずセルフレビューを回す。** 指摘 1 件だけを直して即 push せず、そのラウンドの指摘を根本原因でまとめ、差分全体をローカルで収束させてから push する。外部指摘が異なる HEAD に対して繰り返されたら、`.claude/rules/ci-workflow.md` の「push 後: レビューコメントに対応する」の閾値で止まり、ユーザーに相談する。
