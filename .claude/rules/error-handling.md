# エラーハンドリングの設計

エラーを「値として返すもの」と「投げるもの」に分け、返す側は呼び出し元が網羅的に扱える型で表現する。`robustness.md` が「不正な状態を作れない設計」を扱い、本ルールは「起きた失敗をどう表現し、どこまで運ぶか」を扱う。

## 原則 1: 予期されたエラーは値で返し、予期しないエラーは投げる

| 種別             | 定義                                   | 扱い                     | 例                                                       |
| ---------------- | -------------------------------------- | ------------------------ | -------------------------------------------------------- |
| 予期されたエラー | 正常系の一部として起こりうる分岐       | 戻り値の型に含めて返す   | 対象が存在しない、入力が不正、外部サービスのタイムアウト |
| 予期しないエラー | 起きたらプログラムかインフラ側の不具合 | 投げて上位の監視へ届ける | 接続断、メモリ不足、到達不能なはずの分岐                 |

境界は **呼び出し元がその場で意味のある対処を選べるか**。選べるなら値で返す。選べないなら投げる。

## 原則 2: エラー型は網羅可能に定義する

失敗理由を 1 つの汎用型に潰すと、呼び出し元は分岐を書けず、失敗理由が増えても気づけない。判別可能な union で表現し、呼び出し元が網羅的に扱えるようにする。

```typescript
// ❌ 何が起きたか呼び出し元が判別できない
function getData(): Result<Data, Error>;

// ✅ 理由ごとに分岐でき、増えたときは型が教える
type GetDataError =
  { type: 'NOT_FOUND'; id: string } | { type: 'VALIDATION_ERROR'; message: string };
function getData(): Result<Data, GetDataError>;
```

## 原則 3: 捕捉した例外は分類してから返す

外部から飛んできた例外をそのまま自分のエラー型に載せると、予期しないエラーまで「予期されたエラー」に化けて監視から消える。捕捉したら分類し、自分が意味を与えられるものだけを値にして、残りは再スローする。

## 原則 4: 原因を捨てない

新しいエラーで包むときは元のエラーを cause として繋ぐ。メッセージだけを文字列連結して投げるとスタックトレースが切れ、発生源を追えなくなる。

## 原則 5: 握りつぶさない

ログ出力だけして処理を続けるのは、失敗を隠して後続を壊す。呼び出し元へ返すか、投げて監視へ届けるかのどちらかを選ぶ。

## レイヤーごとの責務

| レイヤー                                                        | 責務                                                         |
| --------------------------------------------------------------- | ------------------------------------------------------------ |
| 外部境界（リクエストハンドラ・外部 API クライアント・永続化層） | 外部の例外・エラーレスポンスを自分のエラー型へ分類する       |
| ドメイン / サービス                                             | 予期されたエラーを型に載せて返す。予期しないものは通過させる |
| 利用者に面する入口                                              | エラー型を網羅的に扱い、利用者向けの表現へ変換する           |

## 禁止パターン

| パターン                                              | 問題                                                   |
| ----------------------------------------------------- | ------------------------------------------------------ |
| メッセージだけを連結して新しいエラーを投げる          | スタックトレースが切れ、発生源を追えない。cause で繋ぐ |
| 捕捉してログ出力だけで続行                            | 失敗が隠れ、監視に届かない                             |
| エラー型を汎用型（`Error` / `any` / `unknown`）にする | 呼び出し元が分岐を書けない                             |
| 捕捉した例外を分類せずそのまま自分のエラーにする      | 予期しないエラーが予期されたエラーに化ける             |

## 生の try-catch を書いてよいケース

原則として、失敗しうる処理は結果型を返す仕組みで包む。生の try-catch を書くのは次のときだけ。

1. `finally` でリソースを解放する必要がある（獲得と解放を対で扱う仕組みを先に検討する）
2. 捕捉した例外を分類し、予期しないものを再スローする

### try-catch ガードは呼び出し箇所ごとに書く

例外を握るだけの薄い処理を、呼び出し元の操作名を文字列で受け取る共通ヘルパー（例: `guard('methodName', () => sdk.methodName(...))`）に切り出すと、渡した文字列と実際に呼ぶメソッドが一致しているかを型で確かめられなくなる。呼び出しもコールバックで一段挟まり、直線的に読めなくなる。

握る対象が1関数あたり1呼び出しで、各呼び出しが短いなら、その場に try-catch を直接書く方が短く、型で守られる範囲も広い。同型の try-catch が複数並ぶと自動レビューは共通化を推してくるが、重複の解消より直線的に読めることを優先してよい。

## 実現パターンの例

言語・ライブラリによって手段は変わるが、代表的な組み合わせは次のとおり。

| 原則                       | パターンの例                                                                                                                       |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 予期されたエラーを値で返す | Result / Either 型で返す（例: TypeScript + Effect の `Effect<T, E>`、Rust の `Result<T, E>`、関数型ライブラリの `Either`）         |
| 捕捉した例外の分類         | 網羅的なパターンマッチで分類し、未知のケースは再スローする（例: ts-pattern の `match().otherwise()`、Rust の `match`）             |
| 原則の自動強制             | 静的解析ルールで違反パターン（cause 無しの再スロー・握りつぶし・曖昧なエラー型など）を検知する（例: ast-grep, ESLint custom rule） |
