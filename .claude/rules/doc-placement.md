# ドキュメントの置き場所（コード近接を優先する）

実装とドキュメントの乖離 (drift) は、**コードを見れば分かる事実を `.md` に転記したとき** に起きる。転記は必ずズレる。書く前に「この情報の SSOT はどこか」を決め、コードが SSOT なら `.md` に書かず、コードの近くに書く。

`evergreen-documentation.md` の SSOT 原則の運用版。前者が「重複させるな」、本ルールが「ではどこに置くか」を決める。

## 配置の判断表

| 情報の性質                                          | SSOT            | 置き場所                                                                                                            |
| --------------------------------------------------- | --------------- | ------------------------------------------------------------------------------------------------------------------- |
| スキーマ / カラム割り当て / enum の値域             | コード          | 定義の JSDoc / docstring (例: schema 定義ファイルの enum / column 定義)                                             |
| 関数の挙動・引数・戻り値・使用上の注意              | コード          | その関数の JSDoc                                                                                                    |
| config の値・環境差分・binding                      | config ファイル | config / IaC / manifest ファイルのコメント                                                                          |
| CLI コマンドの使い方・意図                          | CLI             | サブコマンドの help text                                                                                            |
| 設計判断の WHY (なぜこの構造か / なぜ却下したか)    | ドキュメント    | `docs/plans/` `docs/superpowers/plans/` `docs/superpowers/specs/`（実装完了までの一時置き場。寿命は後述の節を参照） |
| 運用手順 (rotation / onboarding / トラブルシュート) | ドキュメント    | `docs/` / `docs/runbooks/` / infra ディレクトリの README                                                            |

判断基準: **「コードや config を変えたら、この記述も直さないと嘘になるか?」** → なるなら SSOT はコード側。`.md` には書かず、コードのコメントに書いて `.md` からは 1 行で参照する。

## `.md` に書いてよいもの

- コードに表現できない **WHY** (ビジネス制約・設計判断・トレードオフ・却下した代替案の理由)
- コード外の世界の **運用手順** (外部サービス連携・secret rotation・dashboard 設定など SSOT がコードに無いもの)
- 複数コンポーネントにまたがる **アーキテクチャ図** (どれか一箇所のコードには属さない俯瞰)

変更履歴（`CHANGELOG.md`、`.changeset/*.md`）は履歴を残すためのファイルで、配置と鮮度の方針の対象外。

## `docs/plans/` `docs/superpowers/plans/` `docs/superpowers/specs/` の寿命（消費されたら削除する）

上表の `docs/plans/` 系ディレクトリは、対応する実装が完了した時点で価値を失う使い捨てのメモである。実装 PR がマージされる瞬間が消費のタイミングになる（`.changeset/*.md` と異なり、消費の実行は CI ではなく実装 PR のセルフレビューで手動で行う）。

1 本の plan / spec は、複数のファイルから `§5.2` のようなセクション番号で参照されることがある。ファイル名を省略しセクション番号だけで参照するコメントも混じるため、ファイル名の `grep` だけでは参照箇所を網羅できない。削除するときは次の手順を踏む:

1. `grep -rn "<ファイル名>"` で直接参照している箇所を洗い出す
2. 1 の結果だけでは足りない前提に立ち、その plan / spec が扱う機能のディレクトリ（実装対象のサービス層・スキーマ・関連テスト）を、ファイル名を伴わない `§N` 参照も含めて目視で確認する
3. WHY が単一ファイルに閉じるなら、その参照元のコメントへ移す。複数ファイルが依存する横断的な設計判断（cross-cutting invariant）なら、同じ内容を参照元ごとに複製せず `docs/design/` へ昇格させ（「`.md` に書いてよいもの」の複数コンポーネントにまたがるアーキテクチャ図に該当）、各参照元のコメントは昇格先を指すよう付け替える
4. 全参照箇所の手当てが終わってから、plan / spec ファイル自体を削除する（アーカイブしない。経緯は git log が持つ）

判断基準: **「この PR で、plan / spec に書かれた設計は実装され終わったか？」** フォローアップ TODO が残る、他ファイルからの参照がまだ手当てできていない、または段階的にしか実装しないなら残す。残す場合は次の節の猶予宣言を書く（何もしないと鮮度チェックで fail する）。

手順 4 の「リンク切れを残さない」は `bun scripts/docs-lifecycle/run.ts` が検知する。ただし lint が拾えるのは **`docs/...` の形でパスを含む参照と、doc 内の相対リンクだけ**。次の 2 つは検知できないので、手順 1〜2 の grep は省略できない。

- `§5.2` のようにセクション番号だけで参照しているコメント
- `2026-07-23-foo.md` のようにパスを伴わないファイル名だけの言及

## 触られていない doc は消すか見直す

更新が止まった doc は、次のいずれかの状態にある。**どれであっても、そのまま次の実装の根拠にすると誤る。**

- 実装が完了して不要になった（消費済み）
- 実装が先に進み、記述が実態とズレた
- 設計途中で放置され、前提が変わった

そのため「内容が正しいか」ではなく **「最後に触られてから何日経ったか」** を機械的な代理指標にして、見直しを強制する。`bun scripts/docs-lifecycle/run.ts` が最終コミット日からの経過日数で検知し、違反があれば非ゼロで終了する。CI で回すかどうかは各リポジトリのワークフロー次第。lifecycle 区分（ephemeral / durable / generated）と、パス由来の既定の割り当て・閾値の SSOT は `.config/docs-lifecycle.json`。

この設定ファイルは ziku でテンプレートから配られる。**リポジトリ固有の事情を設定に書かない。** 双方向同期でそれが他リポジトリへ流れ込む。個別の doc の事情は、次節の frontmatter で doc 自身に持たせる（生成物なら `lifecycle: generated` を生成スクリプトが出力する）。

### stale と報告されたときの選択肢

上から順に検討する。**削除が第一候補**で、猶予は「まだ実装中」が本当のときだけ使う。

1. **削除する**：実装が済んでいる。手順は前節
2. **WHY を参照元へ移す**：単一ファイルに閉じる設計判断なら、その参照元のコードコメントへ移してから削除
3. **`docs/design/` へ昇格させる**：複数ファイルが依存する横断的な設計判断。昇格先を `lifecycle: durable` にする
4. **猶予を宣言する**：実装が進行中で、期限内に消費する見込みがある
5. **`lifecycle: durable` を宣言する**：長期保持する WHY 集約 doc として扱う

### frontmatter による宣言

| 宣言                                         | 効果                             | 使う場面                                             |
| -------------------------------------------- | -------------------------------- | ---------------------------------------------------- |
| `lifecycle: durable`                         | 長期保持の閾値に切り替える       | 複数コンポーネントが依存する WHY を集約している      |
| `lifecycle: generated`                       | 経過日数を見ない                 | コードから生成され、生成チェックが鮮度を担保している |
| `review-by: YYYY-MM-DD` + `review-reason: …` | その日まで鮮度チェックを保留する | 実装が進行中で、まだ消費できない                     |

```markdown
---
review-by: 2026-09-01
review-reason: データストア移行は段階リリースで、最終フェーズの完了まで設計を参照する
---
```

`review-by` は理由と対で書く（片方だけは lint が拒否する）。期限を過ぎると stale とは別に review-expired として報告されるので、期限を延ばすときは理由も現状に合わせて書き直す。

**中身を見ずにコミット日だけ更新して延命しない。** それはチェックを形骸化させるだけで、乖離した doc はそのまま残る。触るなら実装と突き合わせて直す。

### 再発防止策は文書を最後の手段にする

失敗の再発を防ぎたいとき、`.md` への追記は「読んだ人が覚えていれば防げる」以上の力を持たない。次の順で上から検討し、採れる最上位の段に置く。提案には「どの失敗を、どの時点で、何が検知するか」を書く。

| 段  | 何で防ぐか                                   | 効く条件                                   |
| --- | -------------------------------------------- | ------------------------------------------ |
| 1   | 型やスキーマ（不正な状態を表現できなくする） | 失敗がコードの状態として表せる             |
| 2   | テスト、lint、CI（壊れたら赤くなる）         | 失敗が実行または静的検査で観測できる       |
| 3   | フック（実行前に止める / 実行後に知らせる）  | 失敗がツール呼び出しやコマンドとして現れる |
| 4   | 文書（`.claude/rules/` や runbook）          | 上の 3 段で表せない判断や運用手順          |

「設定が dashboard 側だけ取り残される」のような、コードの外にある失敗も、まず「設定をコードに引き寄せて 1〜2 段で検知できないか」（IaC に書く、実値を CI で照合する）を検討してから文書に落とす。

### 一時 doc を作る前に検討する逃がし先

`.md` を新規に作るのは、逃がせる先が無いときだけにする。

| 状況                                    | 逃がす先                                                       |
| --------------------------------------- | -------------------------------------------------------------- |
| 1 本の PR で実装し切れる                | PR description（doc を作らない）                               |
| 段階的に実装する / フォローアップが残る | GitHub issue                                                   |
| 設計判断が確定した                      | 実装のコードコメント・JSDoc                                    |
| 対話中の思考整理・作業計画              | `.claude/plans/`（gitignore 済み。リポジトリにコミットしない） |

## 既存ドキュメントを触るとき

- スキーマ表 / カラム表 / config 値の一覧が `.md` にあったら、コードに同じ定義があるか grep する。あれば `.md` 側を消し、コードの定義 (JSDoc 付き) を SSOT として参照する 1 行に置き換える。
- 役目を終えた設計メモ (後継ドキュメントに置換された / 不採用が確定した案) は削除する。経緯は git log が持つ。後継ドキュメント側を自己完結させてから消す (リンク切れを残さない)。`docs/plans/` 配下の消費トリガーは上記の節を参照。
