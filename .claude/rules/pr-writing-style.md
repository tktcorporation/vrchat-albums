# PR 本文の書き方（pr-impact-review / pr-first-reader-check / technical-writing-style 準拠）

## 原則

PR を作るときは、本文を **pr-impact-review**（PdM 視点・価値判断）、**pr-first-reader-check**（初見レビュアビリティ）、**technical-writing-style**（文章としての品質）の3スキルの観点で書く。投稿前に3スキルでセルフチェックしてから出す。

詳細はスキル本体を読む: `@.claude/skills/pr-impact-review/SKILL.md`, `@.claude/skills/pr-first-reader-check/SKILL.md`, `@.claude/skills/technical-writing-style/SKILL.md`

## 本文に含める（pr-impact-review）

価値判断は「読み手が go/no-go を切れる材料」を渡すために書く。

- **全体像（冒頭1〜2文）**: この変更は何で、どの文脈・取り組みのどの部分か。背景を知らないレビュアーが「何を見せられているか」を最初に掴める粒度にする。
- **ユーザー価値の変化（before → after）**: ➕ 良くなること（誰の何が）/ ➖ 失う・負担になること（トレードオフ）/ 👁 ユーザーに見える変化（UI・挙動・レスポンス・出力・文言）。**プラスとマイナスの両方**を出す。「マイナスなし」なら本当にそうか疑ってから書く。
- **依頼・イシューの意図との整合**: 狙い（記載 or 推測）と実際が【狙い通り / 一部ズレ / 別物】か。
- **想定外の変化**: 宣言していないのに起きるユーザー可視の挙動変化（サイレント仕様変化）があれば明記する。
- 技術用語はユーザー体験に翻訳する（例: 「キャッシュキーが変わる」→「デプロイ直後に一覧を開いた人へ古い件数が見える」）。

内部リファクタ・typo・コメントのみなど、ユーザーが受け取る価値が一切変わらない PR は「ユーザー価値の変化なし」と一言で結論づけてよい（無理に懸念を盛らない）。

## 初見に通じるように書く（pr-first-reader-check）

別チーム / 入社直後の初見レビュアーが、この PR だけを見て意味を取れるように書く。

- **内輪語を出さない**: issue/PR にしか登場しない呼び名（「軸B」「Phase-2」等の企画上の分類・通し番号）、未定義の略語、暗黙の前提（「いつものフロー」「前回の議論どおり」）を排除する。関連 Issue は番号＋1行要約で参照し、PR 外参照はリンク or 自己完結させる。コード/プロダクトに実体がある用語（grep で定義に辿れる名前）は残してよい。
- **可読性**: 一文一義（50〜60字目安）、主語と述語を近づける、名詞化を動詞に（「算出を行う」→「算出する」）、回りくどい述語を言い切る（「下がる方向で動く」→「下がる」）、結論を先頭に（BLUF）。

## 文章としての品質を整える（technical-writing-style）

pr-first-reader-check が「文脈が伝わるか」を見るのに対し、technical-writing-style は PR 本文を含む対外的な日本語技術文書全般の**文章作法**を見る。両者は重複せず併用する。

- **LLM 口調の排除**: 「重要なのは〜である」等の予告と総括、「正面から扱う」等の姿勢だけの宣言、「不可欠」「多角的」等の空虚な形容、「〜において」等の内容のない接続表現を使わない。
- **論証の厳密さ**: 因果を主張するときは機構（なぜそうなるのか）を一文で示す。異なる原因を一括りにしない。根拠なく推量表現（「かもしれない」）で主張を弱めない。
- **段落構成**: 一段落一トピック。段落冒頭で前段落との論理関係を接続表現で示す。
- **冗長の排除**: 同じ主張を場面描写→要約で二度書かない。中間段階の説明は読み手が自力で補えるなら書かない。
- **見出し**: 手順だけを述べる見出しや、結論を先に明かす「セリフ」見出しにしない。内容を特定できる句にする。

## PR 作成前のセルフチェック（必須）

PR を作る前に、本文だけでなく **差分に含まれるコメント/docstring** も点検する。コメントのルール（`@.claude/rules/evergreen-documentation.md`）を PR フローに組み込むもので、別クローンや YAML など、ルールが自動ロードされない場所で書いたコメントを取りこぼさないために毎回通す。

1. **evergreen-comment チェック**: 差分の全コメント（言語問わず。`.yml`/`.yaml` の CI 設定・Dockerfile も含む）が「現在の WHY」だけになっているか。次が混じっていたら、現在の状態だけで意味が通る形に直し、理由は PR 本文／コミットへ移す。
   - 履歴・経緯: 「既存は〜だった」「以前は〜」「〜のため崩れが蓄積していた」「従来は」「legacy」
   - 変更前を前提にした理由: 「X を追加したので〜」「最低を 400 にしているのは最低が 500 だと〜」
   - WHAT の重複（コードが既に語ること）、コミット SHA / PR 番号 / 個人名への参照
2. **初見レビュアビリティ チェック**: 上の pr-first-reader-check の観点（内輪語・未定義略語・暗黙の前提・可読性）を通す。
3. **文章規範チェック**: 上の technical-writing-style の観点（LLM 口調・論証の厳密さ・段落構成・冗長・見出し）を通す。

3つのチェックで見つけたものは投稿前に直す。`gh pr create` 後にも同趣旨を促す PostToolUse hook があるが、別リポジトリのクローンでは発火しないため、このルールを正本として作成前に必ず実行する。
