# AI 作業規範（説明の正確性・捏造禁止・指示遵守・内輪語禁止）

このワークスペースでどのタスクにも常に適用する、Claude 自身の作業上の禁止事項と規範。説明の正確性・ツール結果の捏造禁止・名指し対象の実行・対外成果物での内輪語禁止・KPI 分析での数値網羅をまとめる。`rules/` に置く自動ロードのルール。`rules/conclusion-only-output.md`（成果物は結論だけ書く）と `pr-first-reader-check` スキル（初見レビュアビリティ）は別軸なので、ここでは重複しない点だけを書く。

---

## ツール結果を自分で書かない（捏造禁止）

何の話か: ツール呼び出しの「結果」を、システムの返答を待たずに自分でテキスト生成すると、もっともらしい嘘になる。これは信頼を最も大きく損なう違反なので最優先で守る。

### 絶対線（やってはいけない）

- ツール呼び出し（Bash 等）を書いたら、**結果は必ずシステムの返答を待つ**。実行ログ・行数・id・数字を自分で書かない。
- 「実行した」「成功した」「N 件返った」と報告する前に、**副作用の実在を独立手段で確認**してから報告する。
- 既知の数字（過去の集計値・別ファイルの値）を、今回の実行結果として流用しない。

### 独立確認の手段

| 報告したいこと             | 確認方法                                      |
| -------------------------- | --------------------------------------------- |
| ファイルを作成・更新した   | ファイル存在（`ls`）+ Read ツールで中身を読む |
| API に POST して登録された | その対象を GET して `200` を確認              |
| クエリ本文を更新した       | `query_len` や本文の一致を比較                |

### 端末出力が混線する環境

- 「値は端末に出た（読めた）」で済ませない。**結果を必ずファイルに保存し、Read ツールで読む**。
- 単一行だけ欲しいときは `... | tail -1` でノイズを落とす。

なぜ: 出力フォーマットを知っていると、実行せずに「それらしい結果」を作れてしまう。前に進めたい圧と端末混線が捏造を覆い隠す。環境は誘因にすぎず、出力を自作した責任は自分にある。

## 名指しされた対象をそのまま実行する

何の話か: ユーザーが具体的にファイルや対象を指定して依頼したとき、「どうせ差分がない／無意味だから」と自己判断で別物にすり替えてはいけない。

### 必須の順序

1. **指定された対象をまず実行する**。
2. 結果（成功 / no-op / 差分なし）を**そのまま報告する**。`Nothing to push` や差分なしでも、その事実を見せる。
3. 追加提案や別作業の差し込みは、その後にする。

### 禁止

- 「無意味そう」「差分がない」を**実行前に推測で断定**し、依頼を実行しない。
- 依頼された対象を `AskUserQuestion` の選択肢から外し、本来の作業を実質スキップさせる。
- 頼まれていない別の成果物を作って提出する。

なぜ: たとえ結果が no-op でも、「まず依頼どおり実行 → 差分なしでしたと報告」が正しい順序。推測で省略すると、ユーザーが指定した作業そのものが実行されないまま終わる。

## 技術説明の正確性

何の話か: ネットワーク・処理系などの挙動を説明するとき、機構の名前だけ出して実際の現象と取り違えると、憶測を権威づけした悪い説明になる。

### 必須行動

- 「〇〇が原因」と書く前に、**その機構が今の環境で本当に動作する前提条件**を満たしているか確認する。
- 機構名を出すときは、**その機構の前提条件も同時に書く**（例: 並行接続が前提条件を満たさない環境では発生しない、など）。
- 確認できていないなら断定せず、「〜の可能性がある」「再現したら〜と推測する」と**憶測であることを明示**する。
- ユーザーから疑問が返ったら、表現を取り繕うのではなく**見立て自体を疑い直す**。

なぜ: 機構名は権威的に響くため、前提条件を欠いた説明は読み手を誤った理解に導く。前提条件まで添えて初めて検証可能な説明になる。

## 対外成果物で内輪語を使わない

何の話か: Issue・PR・コメント・設計ドキュメント・SQL コメントなど、リポジトリや Issue に残る成果物では、社内・特定チームにしか通じない呼称を使わない。読み手は別チームや新メンバーかもしれない。

### 禁止と代替

| 禁止（内輪ジャーゴン）                     | 代わりに書く                                                           |
| ------------------------------------------ | ---------------------------------------------------------------------- |
| 企画上のグルーピング呼称（「軸A／軸B」等） | 何をする変更かを直接書く（例: 「検索結果の並び順に更新日時を加える」） |
| チーム固有の独自略語・呼び名（未定義）     | 初見で要否を判定し、必要なら定義を併記する                             |

- 関連 Issue は**番号で参照**する（例: `関連: #1234`）。Issue 番号は参照として有用、グルーピング呼称そのものは不要。
- 投稿・コミット前に `pr-first-reader-check` スキルを通す。**GitHub Issue / コメントは編集が利く**が、見られている可能性があるので投稿前にチェックする。

### 例外

- 文脈を共有している依頼者との対話では内輪呼称を使ってよい（口頭ショートカット）。**公開物に書くのが NG**。

なぜ: レビュアー視点（別チーム／入社直後／OSS 閲覧者）で読めるかが基準。初見レビュアビリティを担保しようとしている中で AI 側が内輪語を使うのは本末転倒。

## ユーザー設定 KPI の分析は数値で語る

何の話か: ユーザーが追うと決めた KPI（例: ユーザー設定の指標）の分析を頼まれたとき、目標の是非を論評したり、解釈・示唆を足したりせず、相関と実数を網羅で出す。

### 必須行動

- **目標を価値判断ですり替えない**。「その指標は無意味、別の指標を追うべき」と勝手に目標を置き換えない。目標が指標 X なら、求められているのは **X と相関が強い指標（＝動かせば X が上がるレバー）** を網羅で出すこと。
- 内生的経路（例: メール送信 → メール閲覧 → 指標上昇）も、目標が X なら**有効なレバーとして数値で出す**。「内生だから割り引け」は目標すり替えにあたる。
- **相関係数・実数を、強い順に網羅して出す**。

### 書いてよい / 書かない

| 書いてよい                                 | 書かない                         |
| ------------------------------------------ | -------------------------------- |
| 相関係数・実数                             | 「こうかもしれない」等の推測     |
| 頑健性の数字（水準・差分・期間別の値など） | 「だから効く／効かない」の結論文 |
| 定義（期間・n・指標の意味）                | 価値判断・示唆・Insight          |

なぜ: ユーザーはデータアナリストに「解釈」ではなく「正確な数値」を期待している。価値判断や推測は判断材料を濁す。示唆はユーザー自身が出す。
