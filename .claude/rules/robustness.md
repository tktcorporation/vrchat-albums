# 堅牢性の設計

**「動かないコードは書けない」設計を、「動かないコードを見つける」テストより上に置く。** 保証手段の優先順位は 型 > 静的解析 > ランタイム検証 > テスト。上位で防げるものを下位に降ろさない。

`error-handling.md` が「起きた失敗をどう表現するか」を扱い、本ルールは「そもそも不正な状態を作れないようにする」設計を扱う。

## 原則 1: 不正な状態を表現不可能にする

ありえない組み合わせが型として作れるなら、いつか作られる。状態は独立したフラグの集合ではなく、取りうる形の union として定義する。

```typescript
// ❌ isLoading=true かつ data!=null が型として作れる
interface State {
  isLoading: boolean;
  data: Data | null;
  error: Error | null;
}

// ✅ ありえない組み合わせが型レベルで排除される
type State =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: Data }
  | { status: 'error'; error: Error };
```

## 原則 2: 分岐は網羅性を型に担保させる

union の分岐を条件文で書くと、値が増えたときに漏れても気づけない。網羅性を検査できる形で分岐し、値の追加がコンパイルエラーになるようにする。条件文で書いてよいのは、単純な真偽判定だけ。

## 原則 3: Parse, Don't Validate

境界では検証と型変換を同時に行い、検証を通った事実を型に持たせる。検証後も未加工の型（`string` のまま等）に留めると、下流が再度検証を強いられ、漏れが生まれる。

検証すべき境界は、外部からのリクエスト、外部 API のレスポンス、永続化層からの読み出し、設定・環境変数、ファイル入力。

## 原則 4: 同種の値は型で区別する

同じ表現を持つ別種の識別子（利用者 ID と対象 ID がどちらも文字列など）は、取り違えてもコンパイラが助けてくれない。名目的に区別できる型を与えて、引数の入れ違いを型エラーにする。

## 原則 5: 早期リターンで絞り込む

前提を満たさない入力は入口で弾き、以降のコードでは絞り込まれた型だけを扱う。深い入れ子と、後続での再チェックを同時に消せる。

## アンチパターン

| パターン                       | 問題と代替                                                               |
| ------------------------------ | ------------------------------------------------------------------------ |
| `any` / `unknown` の安易な使用 | 型の恩恵を全部捨てる。境界のスキーマから型を導出する                     |
| 型アサーション（`as`）の濫用   | 実際の値と乖離しても検知できない。検証付きの変換を通す                   |
| オプショナルチェーンの過剰使用 | 不在が正常なのか異常なのか読めない。明示的なチェックと早期リターンにする |
| 分岐漏れを実行時に気づく設計   | 網羅性検査のある分岐に置き換える                                         |

## 実現パターンの例

ライブラリによって手段は変わるが、代表的な組み合わせは次のとおり。プロジェクトが採用しているライブラリを確認し、それに合わせる。

| 原則             | パターンの例                                                                                                                                      |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 網羅性のある分岐 | 網羅性を検査できるパターンマッチで分岐する（例: ts-pattern の `match()` + `.exhaustive()`）。網羅性より柔軟性を優先する場合だけ既定ケースへ落とす |
| 境界での parse   | スキーマ定義から型を導出し、境界で検証と変換を同時に行う（例: Zod スキーマ + `z.infer`。失敗を値で扱うなら `safeParse`）                          |
| 同種の値の区別   | 名目的に区別される型を与える（例: Zod の `.brand<'Name'>()`）                                                                                     |
