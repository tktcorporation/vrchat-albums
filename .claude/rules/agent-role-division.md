メインセッションは指揮（タスク分解・設計判断・成果の受け入れ判定・ユーザーとの対話）に専念し、実働（コード編集・探索・機械的な一括作業）は Task/Agent ツールのサブエージェントへ委譲する。サブエージェントのモデルは、呼び出し側や定義で指定しない限り Sonnet になる（`subagent-model-policy.md`）。

そうする理由は 2 つ。メインのコンテキストは全体像を保持するために使いたいが、実装のためにファイルを読み込むとその余地が削られ、設計判断の質が落ちる。そして実装・探索・一括置換は、方針が確定していれば Sonnet で十分な精度が出る。

## 役割分担

| 作業                                                     | 担当   | 補足                                                                       |
| -------------------------------------------------------- | ------ | -------------------------------------------------------------------------- |
| 要件確認・方針の合意・最終報告                           | メイン | ユーザーとの対話はメインが独占する。サブへは確定した方針だけを渡す         |
| タスク分解、委譲の粒度と順序の決定                       | メイン |                                                                            |
| 設計判断（複数案のトレードオフ比較、根本原因の診断）     | メイン | `upstream-fix` スキルの診断はメインで行う                                  |
| 成果の受け入れ判定（差分を読む・品質ゲートを回す）       | メイン | 下の「成果は必ず検証する」を参照                                           |
| コミット / push / PR 作成                                | メイン | 履歴と対外成果物に責任を持つ操作は委譲しない                               |
| コード実装・テスト追加                                   | サブ   |                                                                            |
| コードベースの探索、変更箇所の特定                       | サブ   | 読むだけなら `Explore`                                                     |
| 機械的な一括変更（リネーム・パターン置換・同型の横展開） | サブ   | 対象がファイル単位で交わらないなら並列に投げる                             |
| lint / test を通すまでの修正ループ                       | サブ   | 実装の委譲時に完了条件へ含める。別タスクとして後から投げ直さない           |
| 実装に付随する doc 更新 / changeset の下書き             | サブ   | 対外に出る文言はメインが確定させる（`conclusion-only-output.md` の適用先） |

## メインが直接手を動かしてよい例外

委譲のオーバーヘッド（自己完結したプロンプトの作成 + 成果の検証）が、実作業そのものを上回るとき。

- 内容が確定している 1〜2 ファイルの小さな編集
- サブの成果に対する数行の手直し
- rule / plan / 設計 doc 本文の執筆（成果物そのものが設計判断なので、指揮の範囲）

## 委譲するときに渡すもの

サブエージェントはこの会話の文脈を持たない。プロンプトを単体で完結させる。

- 目的 — 何が満たされたら終わりか
- 対象 — ファイル・ディレクトリの具体パス
- 制約 — 適用される `.claude/rules/` のファイル名、壊してはいけない既存の不変条件
- 完了条件 — 通すべきコマンド、書くべきテスト
- 触ってはいけない範囲

「よろしく」「いい感じに」で投げない。上記が書けないなら、分解がまだ終わっていない。

### 並列に投げる条件

同一ファイルを複数のサブが同時に編集すると競合する。並列に投げる条件は「編集対象がファイル単位で交わらない」こと。交わるなら直列にするか、`worktree.md` に従って作業場所を分ける。

対象が交わらなくても、同時に走らせてよい数には上限がある。lint / test / ビルドを回すサブエージェントは実行環境のメモリを食い合うため、`subagent-resource-limits.md` の同時実行数の上限内に収める。

## 成果は必ず検証する

サブの「実装しました」「テストが通りました」を、そのまま自分の報告に流さない。メインが差分を読み、品質ゲートのコマンドを自分で実行して確認する（`agent-work-discipline.md` のツール結果の捏造禁止）。

サブの報告と実際の差分が食い違ったら、実際の差分を正とする。
