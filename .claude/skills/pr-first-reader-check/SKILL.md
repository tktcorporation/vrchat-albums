# 初見の読み手に伝わるかの検査

文章が、背景を知らない読み手に、書き手の意図どおりに伝わるかを確かめて直す。PR 本文に限らず、自分以外が読む文章すべてが対象になる。

確かめ方は 2 つある。1 つは、読み手が詰まる原因（知らない語、回りくどい文、掴めない構造）を書き手が探す**静的点検**。もう 1 つは、知識ゼロの読み手役に実際に読ませて質問に答えさせ、答えを書き手の意図と照らす**理解度テスト**。静的点検は決まりを満たすかを見るだけで、意図が伝わったかは分からない。書き手は文脈を持っているので、自分で読み返しても詰まる箇所に気づけない。伝わったかどうかは、読み手の答えで確かめる。2 つの結果が食い違ったら、理解度テストの結果を正とする。

照らすための答えを先に用意する。書く前（遅くとも点検の前）に「この文章で伝えたいこと」を書き出す。書き出した要点は、文章の冒頭で読み手に宣言する材料と、理解度テストの正解表の 2 つに使う。

## 進め方

1. **伝えたいことを書き出す**：読み手・読後の状態・要点・誤解されたくない点を、文章とは別のメモに書く
2. **冒頭で宣言する**：書き出した要点を、文章の冒頭 1〜3 文で読み手に伝える
3. **静的点検**：語（意味が取れるか）・文（一読で入るか）・構造（一目で掴めるか）の 3 つの観点で、詰まる箇所を直す
4. **理解度テスト**：知識ゼロの読み手役に読ませ、質問に答えさせ、正解表と照らす
5. **伝わるまで繰り返す**：ずれを根本原因でまとめて直し、新しい読み手役で理解度テストをやり直す

理解度テストと繰り返しは、次のどれか 1 つに当てはまる文章で行う。対外に出す文章（書き手のチームの外の人が読む文章）、読み手に判断や行動を求める文章、数段落を超える文章。3 行の告知でも、読み手に行動を求めるなら行う。3 つのどれにも当てはまらない文章（情報を共有するだけの数行のコメントや返信）だけは、書き出し・宣言・静的点検で終えてよい。

## 伝えたいことを書き出す

文章を書く前に、次の 4 項目をメモに書き出す。書き出せないなら、文章の前に考えが固まっていない。

| 項目 | 書くこと | 例（PR 本文） |
| --- | --- | --- |
| 読み手 | 誰が、何を知っていて、何を知らないか | 別チームのエンジニア。この機能の画面は知っているが、集計テーブルの構造と過去の議論は知らない |
| 読後の状態 | 読み終えた読み手が、何を分かり、何をできる状態になっていればよいか | 変更を承認してよいか判断できる |
| 要点（3 つまで） | 読み手に持ち帰ってほしい主張を、それぞれ 1 文で | ①一覧の件数が、退会済みの人を含まない数に変わる ②画面の見た目は変わらない ③過去の月の数字も遡って変わる |
| 誤解されたくない点 | 読み手が取り違えやすい解釈と、正しい解釈 | 「件数が減る＝不具合」ではない。退会済みを数えていたのが誤りだった |

要点は、読み手が自分の言葉で言い直せる粒度にする。「件数の定義を見直した」は要点にならない。何がどう変わるのかが入っていないので、読み手は言い直せない。

要点を 3 つまでにするのは、一度読んだだけの読み手が持ち帰れる主張の数に限りがあるからである。4 つ以上になるなら、文章を分けるか、主張どうしをまとめられないかを考える。

文章に必要な事実（日付、数字、仕組みの実体）を書き手が持っていないと分かったら、この時点で依頼者に確認する。推測で埋めない。

## 冒頭で宣言する

文章の冒頭 1〜3 文で、要点を先に読み手へ渡す。読み手はそれを枠にして、後に続く詳細を「どの要点の裏付けか」と位置づけながら読む。枠が無いと、読み終えてから全体を組み立て直すことになる。

- PR・Issue：冒頭で「何が・どう変わるか」と、読み手に求めること（承認・判断・確認）を書く
- doc・レポート：冒頭で「この文書で伝えたいこと」を要点の数だけ並べ、本文の節をその順に置く
- 依頼・相談・告知：冒頭で「何を決めてほしいか」「何をしてほしいか」「いつから・いつまでに」を書く

書き出したメモは、宣言の材料にするだけで、そのまま本文に貼らない。メモの「誤解されたくない点」や「読み手」の欄は書き手のための情報で、読み手に見せると内部の検討を晒すことになる。

宣言と本文の中身がずれていたら、本文に合わせて宣言を直すのではなく、書き出したメモの要点に立ち返ってどちらが正しいかを決める。

## 静的点検

初見の読み手が詰まる原因は 3 つある。語の意味が取れない、文が頭に入らない、全体の構造が掴めない。どれか 1 つでも残ると、読み手は止まるか読み返す。3 つの観点それぞれで見る。

判断の基準は書き手ではなく読み手に置く。「自分が一度で読めた」は基準にならない。書き手は文脈を持っているので、どんな文でも読めてしまう。

### 語：意味が取れるか

基準は「書き出した読み手が、この文章と、自分で開ける実物（画面・コード・公開された資料）だけで意味を取れるか」。過去の議論や、読み手が開けない資料を知らないと分からない情報は、文章の中で自己完結させる。

同じ語でも、読み手によって残すか直すかが変わる。社内の指標名やテーブル名は、それを日常的に扱うチームのエンジニアには通じるが、営業や経営層には通じない。判定は「社内の語かどうか」ではなく、**書き出した読み手が、その語の指す実物を自分で確かめられるか**で決める。

| 種別 | 例 | なぜ詰まるか |
| --- | --- | --- |
| 企画・議論の中だけの呼び名 | 「Phase-2」「軸B」「A 案」、施策の通し番号 | 画面にもコードにも実体が無く、企画の経緯を知らないと指す対象が分からない |
| 読み手が開けない参照 | 別リポジトリのファイルパス、BI ツールのクエリ番号だけ、リンクの無いチケット番号、社内ドキュメント名 | 読み手はそれを開けないか、存在を知らない |
| 未定義の略語・専門用語 | 社内独自の略語や指標名、「結果整合性」のような概念を前提にした語 | 読み飛ばすか、調べる手間が生じる |
| 暗黙の前提 | 「いつものフロー」「例のフラグ」「前回の議論どおり」 | 共有されていない前提への参照になっている |
| 内部の名前・ID の生出し | カラム名、マスタの ID、ユーザー ID を説明なしで判断材料にする | スキーマやマスタを知らないと指す対象が分からない |
| 読み手に不要な実装の詳細 | 告知に書いたジョブ実行ツール名や設定の仕組み | 読み手の判断や行動に効かず、知らない語が増えるだけになる |

消さなくてよいもの：

- 読み手が自分で確かめられる語（エンジニアの読み手なら、grep で定義に辿れるサービス名・テーブル名・機能名）
- 画面に出る機能名・プロダクトの正式名称
- 読み手の職種で一般的な用語、ライブラリ・ツールの正式名

直し方は 3 つから選ぶ。

1. **平易な語に置き換える**：「Phase-2 のトレンド」→「新規契約者の利用傾向」
2. **自己完結させる**：読み手が開ける URL にする、チケット番号に 1 行の要約を添える、略語を初出で展開する
3. **削る**：読み手の判断に効かない語や、実体の無いものを指す説明は消す

### 文：一読で頭に入るか

基準は「その文は一読で取れるか。二度読みが要る文はないか」。語が全部分かっても、文が回りくどければ読み手は読み返す。直すのは言い回しだけで、数値・条件・結論は変えない。

| 症状 | 直す型 | 前 → 後 |
| --- | --- | --- |
| 一文に主張が 2 つ以上 | 主張ごとに文を分ける（基準は字数ではなく主張の数） | 「A を見ていなかったため、B に届かない C を含めた値を返していた」→「A を見ていなかった。そのため B に届かない C まで母集団に入り、値が高く出ていた」 |
| 主語と述語が遠い・ねじれる | 主語の直後に述語を置き、長い修飾は前の文に切り出す | 主語と述語の間に長い修飾節が挟まる → 修飾を別の文にほどく |
| 名詞化 | 動詞で書く | 「年収の算出を行う」→「年収を算出する」 |
| 回りくどい述語 | 言い切る | 「下がる方向で動く」→「下がる」 |
| 結論が後ろ | 主点を先に置き、理由を後に続ける | 「〜を踏まえ、〜した結果、X とした」→「X にした。理由は〜」 |
| 二重否定・曖昧な量 | 肯定形・具体値にする | 「リスクがゼロではない」→「起きる可能性がある」／「来週あたり」→「11 月 4 日の週」 |
| 指示語の指す先が遠い | 名詞で言い直す | 「これにより」→「この上限により」 |

### 構造：一目で何が言いたいか掴めるか

基準は「冒頭の数行と見出しだけを読んで、何の話が、いくつあり、結論が何かを言えるか」。語と文が整っていても、構造が見えなければ読み手は全体を自分で組み立て直すことになる。

| 症状 | 直す型 |
| --- | --- |
| 冒頭を読んでも、何の文章か・読み手に何を求めるかが分からない | 冒頭で要点と、読み手に求めることを宣言する |
| 見出しがラベルだけ（「背景」「詳細」「その他」） | 見出しか各節の 1 文目に、その節の結論を書く |
| 要点が本文の中ほどに埋もれている | 要点を冒頭に出し、本文はその裏付けとして並べる |
| 1 つの段落・節に話題が 2 つ以上 | 話題ごとに分ける |
| 箇条書きの項目どうしの関係（原因と結果、前提と帰結）が書かれていない | 因果の連鎖は箇条書きに割らず、接続表現でつないだ文章にする |
| 冒頭の宣言と本文の順番・名前がずれている | 本文の節を宣言と同じ順・同じ名前にする |
| 読み手に求める行動が、書き手の事実とずれている（問い合わせ対応を頼みたいのに「懸念があればコメントを」で終わる） | 書き出したメモの「読後の状態」に合わせて、求める行動を書き直す |
| 読み手の判断に効かない段落（作業の経緯、前置き、本文直後の要約） | 削る |

構造が整っていても、個々の文が長ければ読み手は詰まる。構造を直したあとも、文の点検は省かない。

## 理解度テスト

知識ゼロの読み手役に文章を読ませ、質問に答えさせ、書き出したメモ（正解表）と照らす。読み手役の答えが意図と違えば、読み手の誤りではなく、文章が伝えていない。

### 読み手役の用意

- **起動のしかた**：Agent ツールで、この会話の文脈を持たない新しいサブエージェントを起動する。書き手自身が「知らないつもり」で読むのでは代わりにならない。サブエージェントを起動できない環境では、理解度テストを行わなかったことを報告に書き、読み手役に渡す予定だったプロンプトを添えて依頼者に判断を委ねる
- **立場は実際の読み手に合わせる**：書き出したメモの「読み手」を、そのまま立場として渡す（例：「サービスは使っているが、メール配信の仕組みと社内の企画の経緯は知らない営業担当」）
- **渡すのは実際の読み手が見るものだけ**：文章の全文（タイトル・見出しを含む）と、読み手が実際に見る添付（PR なら差分、資料なら画像）。画像はファイルのパスを渡し、そのファイルだけを開いてよいと伝える。それ以外のファイルやリポジトリを調べない、と明記する。調べられると、文章に書いていないことを補って読めてしまう
- **渡さないもの**：正解表、書き手の意図、静的点検の観点。答えを知った読み手は、伝わっていない文章も読めてしまう。観点を渡すと、読み手役は内容を読み取るかわりに決まりへの違反を探し始め、実際の読み手の読み方から離れる

### 聞くこと

全員に聞く共通の質問と、書き出した要点から作る個別の質問を組み合わせる。

共通の質問：

- この文章は何を伝えようとしているか（自分の言葉で 3 文以内）
- 読み手であるあなたに、何をしてほしいと言っているか
- 冒頭の数行だけを読んだ時点で、何が分かったか
- 読んでいて止まった所（意味の分からない語、何を指すか分からない参照、読み返した文、前と食い違って見えた所、理由が書かれていない主張）
- 読み終えて残った疑問

個別の質問：要点と誤解されたくない点のそれぞれに、1 問ずつ作る。

- **答えを含めない**：「件数は減りますか？」ではなく「この変更で、一覧の件数はどうなりますか。なぜですか」と聞く
- **言い直させる**：要点の文言を当てさせるのではなく、自分の言葉で説明させる。文章の文をそのまま写した答えは、理解ではなく引用でも返せる
- **誤解されたくない点は、取り違えを誘う形で聞く**：「件数が減るのは不具合ですか、意図した変化ですか。根拠も答えてください」
- **読み手の行動を場面で聞く**：読み手に行動を求める文章なら、「お客様からこう聞かれたら、どう答えますか」のように、実際に行動する場面を置いて答えさせる

答え方の指示として、「分からないことは分からないと答える」「推測で補った部分は推測だと明記する」「文章の文をそのまま写さない」を必ず添える。推測で補って正しく答えられた所も、文章に書いていないので直す対象になる。

### 照らし方

要点ごとに判定する。

| 判定 | 条件 | 直す対象か |
| --- | --- | --- |
| 伝わった | 自分の言葉で、正解表と同じ意味を答えた | 対象外 |
| 推測で伝わった | 正しく答えたが、推測だと明記した | 対象 |
| 部分的 | 一部だけ答えた、または根拠を答えられない | 対象 |
| 誤解 | 正解表と違う意味で答えた | 対象（最優先） |
| 伝わらず | 答えられなかった | 対象 |

共通の質問のうち「止まった所」と「残った疑問」の答えは、そのまま直す箇所の一覧になる。そのうち、要点の誤解につながるものや、読み手が求められた判断・行動をできなくなるものを**重い止まり**として扱う。言い回しが少し引っかかった程度のものは軽い止まりで、直すが、ループを終える妨げにはしない。重いか軽いかは、読み手役の申告ではなく、書き手が正解表と照らして判定する。

## 伝わるまで繰り返す

1 ラウンドは「理解度テスト → ずれを根本原因でまとめる → 直す」で回す。

- **根本原因でまとめる**：ずれを 1 つずつ言い換えで潰さない。複数の要点が「部分的」なら、冒頭の宣言が無い、要点を支える根拠が離れた節にある、のような共通の原因を探して直す
- **直し方は静的点検の型を使う**：伝わらない箇所を、言い換えや補足の段落で膨らませない。膨らむと要点がさらに埋もれる。先に削る・並べ替える・言い切る・冒頭で宣言する、で直せないかを見る。ただし、主張の理由や仕組みが欠けていて読み手が止まったなら、その理由を 1 文で足すのは正しい直し方である
- **足りない事実は書き手に聞く**：直すのに書き手が持っていない事実（数字、日付、仕組みの実体）が要るなら、推測で書かずに依頼者へ確認する。確認が取れるまでは、そのずれを「残ったずれ」として報告に載せる
- **読み手役は毎回新しくする**：前の読み手役を再開しない。一度読んだ読み手は、もう知識ゼロではない
- **終わる条件**：2 ラウンド続けて、全要点が「伝わった」になり、重い止まりが無い。1 ラウンドだけでは、その読み手役がたまたま正しく推測できた可能性を外せないので、別の読み手役でもう一度確かめる
- **打ち切る条件**：直しても同じ要点のずれが 3 ラウンド続いたら、文章ではなく要点自体（伝えたいことが多すぎる、読み手の設定が合っていない、主張そのものに根拠が足りない）を疑う。残るずれと、考えられる原因を依頼者に伝えて方針を決める

## 出力フォーマット

ラウンドごとに「理解度テスト」の表を 1 つ作り、上から順に並べる。静的点検と直した結果は、全ラウンド分をまとめて 1 つにする。

```markdown
## 初見の読み手への伝わり方：[文章の名前]

### 伝えたいこと
- 読み手：…
- 読後の状態：…
- 要点：①… ②… ③…
- 誤解されたくない点：…

### 理解度テスト（ラウンド 1）
| 要点 | 意図 | 読み手役の答え | 判定 | 原因 | 直し方 |
| --- | --- | --- | --- | --- | --- |
| ① | 件数が退会済みを含まない数に変わる | 「件数の数え方が変わる」とだけ答え、どう変わるかは推測 | 推測で伝わった | 冒頭が「定義を見直した」で止まり、何がどう変わるかが無い | 冒頭を「退会済みの人を件数から除く」に言い切る |
| ② | 画面の見た目は変わらない | 「見た目は変わらない」 | 伝わった | － | － |

重い止まり：…

### 静的点検
| 箇所 | 文言 | 観点 | 種別 | 直し方 |
| --- | --- | --- | --- | --- |
| タイトル | 「(Phase-2)」 | 語 | 企画の中だけの呼び名 | 削る |
| 本文 2 段落目 | 「下がる方向で動く」 | 文 | 回りくどい述語 | 「下がる」 |
| 見出し | 「背景」 | 構造 | ラベルだけの見出し | 「退会済みの人を数えていた」 |

### 直した結果
- [箇所] 前 → 後

### 残ったずれ
- [ずれ] 直さなかった理由、または書き手に確認が要る事実
```

報告では、何ラウンド回したか、読み手役にどんな立場を渡したか、終わる条件を満たしたかを書く。

## PR に使うときの対象

PR では、本文以外にも読み手が目にする文章がある。次をすべて見る。

1. タイトル
2. 本文
3. コミットメッセージ
4. 差分内のコメント・docstring
5. 新しく導入した識別子・定数名・画面の文言

```bash
gh pr view <PR番号> --json title,body
gh pr diff <PR番号>
# origin/HEAD が未設定だと範囲が空になり、コミットを全部取りこぼすので先に設定する。
git remote set-head origin --auto >/dev/null 2>&1 || true
base="$(git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null)"
git log --format='%h %s%n%b' "${base:?origin/HEAD 未解決。git remote set-head origin --auto を実行}..HEAD"
```

PR の理解度テストでは、読み手役に本文と差分を渡し、「この PR を承認してよいか判断できるか。できないなら何が足りないか」を共通の質問に加える。

## やりがちな失敗

| 失敗 | どうするか |
| --- | --- |
| 伝えたいことを書き出さずに点検を始める | 正解表が無いと、読み手役の答えが合っているかを判定できない。書き出しから始める |
| 要点を「〜について説明する」の形で書く | 要点は主張にする。「何が、どうなる」を 1 文で |
| 読み手役に書き手の意図や背景、点検の観点を渡す | 文章の全文と、実際の読み手が見る添付だけを渡す |
| 答えを含む質問をする（「X ですよね？」） | 「どうなるか」「なぜか」を自分の言葉で答えさせる |
| 前のラウンドの読み手役を再開する | 毎回新しい読み手役を起動する |
| 足りない事実を推測で書き足す | 書き手に確認し、取れるまでは残ったずれとして報告する |
| 自分で読み返して「分かる」と判断する | 書き手は文脈を持つので必ず読める。基準は読み手役の答え |
| 語だけ直して、文や構造を素通しする | 3 つの観点すべてを見る。語が全部分かっても、文や構造で詰まる |
| 文を直すときに意味まで変える | 数値・条件・結論は直す前と一致させる |
| 読み手が普段使う正式名称や用語まで消す | 消すのは、書き出した読み手が確かめられない語だけ |
