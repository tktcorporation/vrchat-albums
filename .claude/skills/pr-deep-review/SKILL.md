# PR 深掘りレビュー（周辺コンテキスト込み）

PR / ブランチ差分を、**diff の外側まで読んで**「仕様通りか・コードとして正しいか・読みやすく作り込まれているか・既存の設計と整合しているか」を判定するスキル。

**レビュー中は作業ツリーを変更しない**: Step 0〜4 を通じて `git diff` / `git show` / `git log` / `rg` など読み取り専用の操作だけを使う。`git checkout` / `git switch` / `git reset` / `git stash` で HEAD・作業ツリー・ブランチ状態を動かさない。別リビジョンの中身を見る必要があるときは `git show <SHA>:<path>` で読むか、`EnterWorktree` / `git worktree add` で隔離した別ディレクトリを使う（`.claude/rules/worktree.md` の「他プロセスの変更を絶対に消さない」と同じ理由。Agent 並列 dispatch で複数のレビュー担当が同じチェックアウトを触ると、他の作業や他レンズの調査結果を壊しうる）。

## 何のためのスキルか（位置づけ）

```
pr-first-reader-check   →  「この説明・コメントは初見に伝わるか」（文章の可読性）
pr-impact-review         →  「これをユーザーに出して良いか」（PdM・ユーザー価値）
pr-deep-review（本スキル）→  「この実装は仕様通りで、技術的に正しく、読みやすく、既存設計と整合しているか」
```

3つは補完関係で、重複しない。本スキルはユーザー価値の増減は判定しない（pr-impact-review の仕事）し、PR本文・GitHubコメントの文章の伝わりやすさも見ない（pr-first-reader-check の仕事）。コード自体の可読性（命名・複雑さ・重複）は本スキルの「コード品質」レンズが扱う。`codex review --uncommitted` など軽量なコードレビューとの違いは、**周辺コードを能動的に読みに行くことを手順として強制する**点にある。差分だけを見るレビューは、次のような問題を見逃す:

- 変更した関数の呼び出し元が、変更後の契約（引数の意味・null許容・戻り値の型）と食い違っていても気づかない
- 同じパターンの実装が他に複数箇所あり、今回の修正が一部にしか適用されていなくても気づかない（同一バグの取りこぼし）
- 変更した値が下流の別モジュール（マスキング処理・シリアライズ・キャッシュ等）でどう扱われるかを確認せず、リスクを見落とす
- バグが無く仕様通りでも、命名が意味不明・条件分岐が複雑・同じロジックが複製されている等、読みにくく保守しづらいコードを「動くから良し」と見逃す

## いつ使うか

- ロジック変更・既存パターンの変更・複数ファイルに影響する変更をレビューするとき
- 「ちゃんとレビューして」「深く見て」「設計も含めて確認して」「他にも同じ修正が要る箇所はないか」といったリクエスト
- PR 作成前のセルフレビューとして、`codex review` より踏み込んだ1回の技術レビューを挟みたいとき

**使わなくてよい場面**: typo 修正・フォーマットのみ・1行の自明な設定変更など、周辺文脈を読む必要が無いほど自明な変更（`codex review --uncommitted` で足りる）。

**`.claude/rules/pr-self-review.md` との関係**: `gh pr create` 前のゲートは、`pr-review-loop` のラウンドを指摘が収束するまで記録することで満たす。本スキルはそのループの 1 ラウンド分のレビュー手順で、ループ自体（収束判定・記録・codex を挟むラウンド）は `pr-review-loop` が担う。

## 手順

### Step 0: 対象とスコープを確定する

```bash
# PR 番号が指定された場合
gh pr view <PR番号> --json title,body,files,baseRefName,headRefName
gh pr diff <PR番号>

# ローカルブランチ / 未コミット (default branch 名は repo により main / master 等で異なるため origin/HEAD から動的に取得する)
# origin/HEAD が未設定なら一度だけ: git remote set-head origin --auto
default_branch="$(git symbolic-ref --short refs/remotes/origin/HEAD | sed 's@^origin/@@')"
git fetch origin "$default_branch"
git diff "origin/$default_branch"...HEAD --stat
git diff "origin/$default_branch"...HEAD

# 関連イシューがあれば本文も取る（Step 2 の基準線になる）
gh issue view <イシュー番号> --json title,body
```

差分の**変更ファイル数・影響範囲**を見て、後述の実行方式（軽量 / フル）を選ぶ。

### Step 1: 周辺コンテキストを集める（省略しない）

**ここが本スキルの核。飛ばすと、以降のどのレンズも「diff しか見ていない指摘」に落ちる。** 変更されたシンボル（関数・クラス・コンポーネント・クエリ）ごとに:

1. **呼び出し元・参照元を洗い出す**: `rg 'funcName\(' -g '!*test*'` のように grep して全箇所を一覧化する。フロントエンドなら import 元、SQL なら参照している別クエリ（chain query 等）
2. **類似の既存実装を探す**: 同じ問題を解いている隣接コードを探す。「この修正パターンが他にも必要な箇所はないか」を機械的に洗う（一部のファイルだけ直して同種バグが他に残る、という取りこぼしが起きやすい）
3. **関連テストの有無と内容を確認する**: 変更後もテストが意味を持つか、カバーされていないエッジケースはないか
4. **対象パスに応じたプロジェクト規約を確認する**: プロジェクトにパスごとの規約表がある場合（例: `src/api/**/*.py` → `api-style.md`、`packages/*/**` → 各パッケージの README）、該当ルールを読む
5. **変更した値が下流でどう扱われるかを追う**: 「この値は次にどこで使われるか」を1段でも辿る（マスキング・シリアライズ・キャッシュ・権限チェックなど、diff に写っていない別モジュールに実装があることが多い）

詳細な集め方は `references/review-lenses.md` の「周辺コンテキストの集め方」を参照。

### Step 2: 4レンズで評価する

各レンズの詳細チェックリストは `references/review-lenses.md`。ここでは要点のみ。

- **仕様面**: イシュー / PR に書かれた狙い（基準線）を差分と突き合わせる。基準線の出どころ（イシュー本文で確認できた／自己申告のみ／記載なし／イシューが無くても下流の実装や呼び出し元が一次情報として基準線を裏付けられる）を区別して書く。要求されている機能の実装漏れ、基準線に書かれていない暗黙の仕様（Step 1 で見つけた類似実装が前提にしている仕様）を満たしているかを見る。
- **コードの正しさ**: バグ・エッジケース・エラーハンドリング・型安全性・セキュリティ（インジェクション・認可漏れ・シークレットやPIIの露出）・パフォーマンス（N+1・無制限クエリ・リソースリーク）。**Step 1 で洗った呼び出し元が期待する契約**（null 許容・単位・タイムゾーン・戻り値の形）と、変更後の実装が食い違っていないか。動作に影響しない純粋なスタイルの指摘（`let`/`const` の使い分け、比較演算子の冗長さ等）は次の「コード品質」レンズに書く。詳細チェック項目は `references/review-lenses.md`
- **コード品質（可読性・設計の筋の良さ）**: この差分**単体**を、既存コードとの整合性とは切り離して評価する。命名が変数・関数・型の意図（ドメイン概念）を表しているか、条件分岐やネストが追いやすいか（ネストした三項演算子・深い if/else ネストは要注意）、同じロジックが複数箇所にコピペされていないか、抽象化の粒度が妥当か（1回しか使わない処理を無理に汎用化していないか＝過剰設計、逆に複数の責務が1つの関数・コンポーネントに詰め込まれていないか＝抽象化不足）。新規に型・クラスを導入している場合は不変条件がコンストラクタ等で保証されているか、内部実装が漏れていないか。**コメント・docstring の初見可読性は `pr-first-reader-check` の担当なのでここでは扱わない**（コード構造そのものが対象）。バグが無くマージ可能な場合でも、この観点の指摘は別立てで書く。
- **全体設計**: 既存のアーキテクチャパターン・責務分割との整合性。**Step 1 で見つけた類似実装との一貫性**（同じ修正が必要な箇所が他にもあるのに一部しか直っていない、車輪の再発明になっていないか）。将来の拡張性・技術的負債。この差分単体の可読性・命名・重複・抽象化の粒度は前の「コード品質」レンズで見るので、ここでは既存コードとの整合性のみを扱う。

**含めないもの**: PR 本文・GitHubコメント・コード中のコメント/docstring の初見可読性（`pr-first-reader-check` の仕事）、ユーザー価値の増減判定（`pr-impact-review` の仕事）。

### Step 3: 自分の指摘を検証する（捏造防止）

Important 相当以上の指摘は、報告前に次を自問する:

- **実際に読んだファイル・行を示せるか？** 示せない指摘（「〜かもしれない」で終わる憶測）は、"要確認" に格下げするか、実際に該当ファイルを読んでから確定させる
- **Step 1 の周辺コンテキストに基づいているか？** diff だけを見た印象で「危険そう」と書いていないか
- 複数の指摘が見つかった場合、Important 以上は可能なら**別の角度から一度読み直して**裏付けを取る。指摘ごとに独立した Agent（`Agent` ツール）へ「この指摘は本当に裏付けられるか、実際にファイルを読んで確認せよ」と投げて検証させてもよい（詳細は `references/review-lenses.md`）

`.claude/rules/agent-work-discipline.md` の「ツール結果を自分で書かない」原則と同じ精神: 読んでいないファイルについて指摘を書かない。

### Step 4: レポートにまとめる

pr-impact-review・pr-first-reader-check と同様、**結論を先頭に**。`.claude/rules/conclusion-only-output.md` に従い、検証の過程（どう調べたか）は残さず、結論と根拠（ファイル位置・再現条件）だけを書く。

**「良い点」は指摘を書く前に最低1つ具体的に洗い出す。** 社交辞令ではなく、実際に読んで判断できた良い設計・妥当な実装判断を書く。的確な良い点を示せると、その後に並べる Critical/Important の指摘も「ちゃんと読んで判定している」という信頼を伴って伝わる。良い点が1つも出てこない場合、Step 1 の読み込みが浅い可能性を疑う。

## 出力フォーマット

```markdown
## PR 深掘りレビュー: [タイトル]

### 判定: 【マージ可 / 要修正 / マージ不可】

[1〜2文で理由]

### 仕様面

- 基準線: [イシュー本文で確認 / 自己申告のみ / 記載なし / 下流の実装が一次情報]
- 判定: 【仕様通り / 一部未実装・ズレ】— [根拠]

### コードの正しさ

| 重大度    | 指摘 | 根拠（file:line、または query ID・URL 等の参照） |
| --------- | ---- | ------------------------------------------------ |
| Critical  | ...  | ...                                              |
| Important | ...  | ...                                              |
| Minor     | ...  | ...                                              |

### コード品質（可読性・設計の筋の良さ）

| 重大度    | 指摘 | 根拠（file:line） |
| --------- | ---- | ----------------- |
| Important | ...  | ...               |
| Minor     | ...  | ...               |

### 全体設計

- 既存パターンとの整合: [...]
- 周辺の類似実装との一貫性: [同じ修正が必要な箇所があれば列挙。無ければ「確認したが他に該当箇所なし」]

### 良い点

- [具体的に]
```

**同じ指摘を複数セクションで繰り返さない。** 該当レンズで1回だけ言い切る。

`ReportFindings` ツールが使える環境なら、指摘をそのツールで構造化して返してもよい。`category` はレンズが分かる値（例: `spec-mismatch` / `correctness` / `code-quality` / `design-consistency`）を目安にしつつ、実際に許可される値は環境依存なので、ツールのスキーマに合わせて調整する。`failure_scenario` は「どんな入力・状態で何が壊れるか / 何が実装漏れになるか」を書く。使えない環境（`ToolSearch` で見つからない場合や、自分がサブエージェントとして起動されていて利用できない場合）は上の Markdown フォーマットで返せば十分で、無理に使う必要はない。

## 実行方式（軽量 / フル）

**軽量とフルの違いは「誰が実行するか」（自分1人 / 複数エージェントで並列化するか）であって、Step 1 の調査の深さを変えるものではない。** 変更ファイルが1つでも、呼び出し元や仕様の一次情報がリポジトリ外（BIツールのライブクエリ、他サービスの API 等）にあり `gh` や社内APIクライアント等でのネットワーク越しの調査が要る場合、実質的な調査コストはファイル数だけでは測れない。

| 状況                                                                                                                                   | 方式                                                                                                                                                                                                                                                                                                                                             |
| -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 変更ファイル数が少なく、呼び出し元・関連仕様もリポジトリ内 grep だけで追える                                                           | 自分（メインエージェント）が Step 1〜4 を順に実行                                                                                                                                                                                                                                                                                                |
| 変更ファイルが多い／呼び出し元が広範囲／リポジトリ外の一次情報（ライブクエリ・他サービス）を複数辿る必要がある／アーキテクチャに関わる | `Agent` ツールで4レンズ（仕様面・正しさ・コード品質・設計）を1メッセージ内で並列 dispatch し、各エージェントに Step 1 の周辺コンテキスト収集手順とその1レンズだけを見る指示を渡して独立に読ませる（`superpowers:dispatching-parallel-agents` と同じ「同一応答内の複数 dispatch＝並列実行」の考え方）。指摘は Step 3 のとおり検証してから統合する |

`Agent` ツールでの並列実行は、メインの会話セッションや `code-reviewer` 系のサブエージェントなど本スキルを想定利用する範囲では使える（`Explore`/`Plan` 等、`Agent` を持たない一部のサブエージェント定義もあるので、その場合は自分で Step 1〜4 を順に実行する軽量方式に切り替える）。`Workflow` ツール（JS スクリプトでの `agent()`/`pipeline()` オーケストレーション）が手元で使える場合はさらに自動化できるが、サブエージェントとして起動されているときは利用できないことがあるため、使う前に `ToolSearch` 等で存在を確認し、無ければ上記の `Agent` ツール並列 dispatch にフォールバックする。雛形は `references/review-lenses.md` にある。

小さい PR にフル方式を使うのは過剰。逆に影響範囲が広い変更を自分一人で読み切ろうとすると Step 1 が浅くなりがち。どちらの方式でも Step 1 は省略しない。

## やりがちな失敗

| 失敗                                                                                    | どうするか                                                                                                                                           |
| --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| diff だけ見て「周辺は確認していません」で終える                                         | Step 1 を飛ばした兆候。呼び出し元・類似実装を最低1つは grep で洗う                                                                                   |
| 「呼び出し元を確認しました」と言いながら根拠（grep結果・ファイルパス）を示せない        | Step 3 で却下。実際に読んだ場所を示せる指摘だけ残す                                                                                                  |
| 複数レンズの指摘を1レンズに混ぜて書く                                                   | レンズごとに分けて書く。読み手が「何の問題か」を判断しやすくする                                                                                     |
| 類似実装が他に複数箇所あるのに1箇所しか確認しない                                       | Step 1-2 のgrepが網羅的か疑う。「他に該当箇所なし」は確認した上で書く                                                                                |
| 全部 Critical にする／逆に全部 Minor にして無難に終える                                 | 重大度表に照らし直す。実際に壊れる条件を言えるかで判定する                                                                                           |
| 「コードの正しさ」をロジックバグだけだと思い込み、セキュリティ・パフォーマンスを見ない  | SQL/コマンドインジェクション・認可漏れ・シークレットやPIIの露出・N+1クエリも同じレンズの対象。`references/review-lenses.md` の詳細テーブルで確認する |
| バグが無く仕様通りなら「良い実装」と判断し、可読性・複雑さ・命名を見ない                | コード品質レンズは独立して評価する。バグ0件でもネストした三項演算子・意味不明な命名・コピペ重複は指摘対象                                            |
| 可読性の指摘を「全体設計」に混ぜて、即興の見出し（過剰設計・カプセル化 等）を作って書く | この差分単体の可読性・複雑さ・抽象化の粒度は「コード品質」レンズの担当。全体設計は既存コードとの整合性だけを書く                                     |
| ユーザー価値の話（プラス/マイナス）や PR 本文の読みやすさまで書く                       | それぞれ pr-impact-review・pr-first-reader-check の仕事。本スキルでは扱わない                                                                        |

## Red Flags（自分がサボっているサイン）

- Step 1 のコマンド（grep・rg 等）を1度も実行していないのに「周辺コードを確認」と書いている
- 「良い点」が空、または逆に指摘が0件で「問題なし」とだけ書いて終わる（小さい変更なら妥当だが、複数ファイルに影響する変更でこれが出たら Step 1 をやり直す）
- 【マージ可 / 要修正 / マージ不可】の判定を出していない
- 仕様面・正しさ・コード品質・全体設計の4レンズのうち一部だけで終わっている
