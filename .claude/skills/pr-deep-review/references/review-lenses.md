# レンズ別チェックリストと周辺コンテキストの集め方

`SKILL.md` の Step 1・Step 2 で使う詳細版。SKILL.md 本体には要点だけを置き、重い参照はここに置く。

## 周辺コンテキストの集め方（Step 1 詳細）

差分に写っているのは「変更後の姿」だけ。以下を辿って「変更が触れる範囲全体」を再構成する。

### 1. 呼び出し元・参照元

- 関数/クラス/コンポーネント: `rg '関数名\(' -g '!*test*'`、`rg 'import.*コンポーネント名'`
- SQL: 同じディレクトリ内の他クエリやビュー・レポートが、変更対象のクエリ/テーブルを参照していないか（分析ツール上のクエリ間依存を辿る）。PIIマスキング等の後処理パイプラインを経由するなら、そのロジックが変更後のカラム名・型でも正しく判定できるか確認する
- API: フロントエンドの呼び出し箇所、他サービスからの利用箇所

呼び出し元ごとに「変更後の契約（引数の意味・null 許容・単位・戻り値の形）を満たしているか」を確認する。

### 2. 類似の既存実装

- 同じディレクトリ・同じモジュールに、今回と同種の処理をしている隣接ファイルがないか
- 「この修正パターンが必要な箇所」を検索語を変えて複数回洗う（例: 同じ関数呼び出し、同じテーブル参照、同じ設定キー）。1回のgrepで0件でも、表記ゆれ（別名・別実装）で見逃していないか疑う
- 見つかった場合、今回の PR で直っていないなら「他にも同じ修正が要る箇所」として指摘する

### 3. 関連テスト

- 変更対象に対応するテストファイルがあるか
- あるなら、変更後もアサーションが意味を持つか（表面上パスするだけで、意図しない挙動を許容してしまっていないか）
- ないなら、追加の要否を「コードの正しさ」レンズで指摘する

### 4. プロジェクト規約

- `CLAUDE.md` の「Rules（自動ロード）」表で、変更したファイルパスに対応するルールを確認する
- スキーマ・ビュー定義に依存する変更なら、そのスキーマの実際の定義（スキーマ管理ファイルやデータウェアハウスのビュー定義ドキュメント等）を確認する

### 5. 下流の扱われ方

- 変更した値・出力が次にどこで使われるかを最低1段階辿る
- 例: クエリに新しいカラムを足す → そのクエリ結果を読むツール（PIIマスキング処理等）でどう扱われるか / 別クエリでJOINキーとして使われるならキーの型・欠損値の扱いは一致するか

## 仕様面レンズ（詳細）

| 確認項目         | 何を見るか                                                                                                                                                                                                                                                                                                            |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 基準線の出どころ | イシュー本文で確認できた／PR説明・コミットメッセージの自己申告のみ／記載なし／イシューが無くても下流の実装（呼び出し元コード・参照している他クエリ等）が一次情報として基準線を直接裏付けられる、のいずれかを区別する。特にデータ分析系の差分は issue が無いことも多く、下流の実装そのものが仕様の一次情報になりやすい |
| 要求の充足       | イシューに書かれた要求が全て実装されているか。部分実装なら明記する                                                                                                                                                                                                                                                    |
| 暗黙の仕様       | Step 1 で見つけた類似実装が前提にしている仕様（例: 既存実装は空文字列を「未設定」として扱う）を今回の実装も踏襲しているか                                                                                                                                                                                             |
| スコープ         | 要求に無い変更が混じっていないか（混じっていること自体は悪ではないが、レビューで指摘する）                                                                                                                                                                                                                            |

## コードの正しさレンズ（詳細）

| 確認項目               | 何を見るか                                                                                                                                                                                                                                                                                                                    |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ロジック               | 差分単体で見て明らかな誤り（境界条件・オフバイワン・符号・優先順位）                                                                                                                                                                                                                                                          |
| 契約整合               | Step 1 で洗った呼び出し元が期待する型・null許容・単位・タイムゾーンと一致するか                                                                                                                                                                                                                                               |
| エラーハンドリング     | 例外・エラーケースが握りつぶされていないか。`.claude/rules/agent-work-discipline.md` の「ツール結果を自分で書かない」と同じ精神で、失敗が静かに成功扱いになっていないか                                                                                                                                                       |
| セキュリティ           | SQL/コマンド文字列を組み立てている箇所でインジェクションの余地がないか、認可・権限チェックが抜けていないか、シークレットやAPIキーがハードコードされていないか、個人情報（email・氏名等）がログ・レスポンス・分析クエリ結果に平文で漏れていないか（社内にPIIマスキングの仕組みがあるなら、その経路を経由しているかも確認する） |
| パフォーマンス・並行性 | ループ内でのDBクエリ発行（N+1）、上限のないクエリ/ループ、ホットパスでの重い処理、複数プロセス/リクエストが同じ状態を同時に更新するときの競合状態、接続やファイルハンドルの解放漏れ                                                                                                                                           |
| テスト                 | 新規/変更ロジックを実際に検証しているか（モックだけで終わっていないか）                                                                                                                                                                                                                                                       |

重大度は以下で判定する（`pr-impact-review` の重大度表と同じ考え方）:

- **Critical**: バグ・データ破損・セキュリティ問題など、マージするとユーザーや運用に実害が出る
- **Important**: 設計上の問題・機能の欠落・テスト不足など、直さないとあとで手戻りになる
- **Minor**: スタイル・最適化余地・ドキュメント不足

動作に影響しない純粋なスタイルの指摘（`let`/`const` の使い分け、比較演算子の冗長さ、命名、ネストの深さ等）はこのレンズに含めず、次の「コード品質レンズ」に書く。

## コード品質レンズ（詳細）

差分**単体**の作り込みを見る。既存コードとの整合性（アーキテクチャ・類似実装との一貫性）は次の「全体設計レンズ」の担当なので、ここでは扱わない。コメント・docstring の初見可読性（Evergreen Comments 原則との整合）は `pr-first-reader-check` の担当なので、このレンズでは扱わない（コード構造そのものが対象）。

| 確認項目           | 何を見るか                                                                                                                                                                      |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 命名               | 変数・関数・型・引数の名前がドメイン概念や意図を表しているか。`a`/`b`/`tmp`/`data` のような無意味な名前、真偽値の意味が呼び出し側から読み取れない引数名                         |
| 制御フローの複雑さ | ネストした三項演算子、深い if/else ネスト（早期リターンで削れるものが放置されていないか）、1つの条件式に詰め込まれすぎた論理演算子                                              |
| 重複               | 同じロジック・同じ条件分岐が複数箇所にコピペされていないか（DRY）。ただし2箇所程度の偶然の一致まで無理に共通化を求めない                                                        |
| 抽象化の粒度       | 単純な処理に不要なクラス・インターフェース・デザインパターンを持ち込んでいないか（過剰設計）。逆に、複数の責務が1つの関数・コンポーネントに詰め込まれていないか（責務分離不足） |
| 型・invariant 設計 | 新規に導入した型・クラスが不正な状態を表現可能にしていないか、カプセル化が適切か、不変条件がコンストラクタ等で保証されているか                                                  |

重大度はこのレンズでは **Important**（放置すると後で手戻りになる。例: 重複ロジックが片方だけ直されて挙動が乖離するリスク）と **Minor**（命名・スタイル・軽微な簡潔化）が中心。読みにくさ自体は直接ユーザーや運用に実害を与えないため、原則 Critical にはしない。

## 全体設計レンズ（詳細）

差分単体の可読性・命名・重複・抽象化の粒度は前の「コード品質レンズ」で見る。ここでは既存コードとの整合性のみを扱う。

| 確認項目           | 何を見るか                                                                                                                                                                                                                                            |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| アーキテクチャ整合 | レイヤリング違反（例: View から直接 DB クエリ）がないか、既存の責務分割に沿っているか                                                                                                                                                                 |
| 一貫性             | Step 1 で見つけた類似実装と同じ考え方で書かれているか。今回だけ違う流儀を持ち込んでいないか                                                                                                                                                           |
| 取りこぼし         | 同じ修正パターンが必要な箇所が他にもあるのに、一部にしか適用されていないケースがないか。**これはコードレビューで最も見落とされやすい**（1箇所の diff だけを見て「直った」と判断し、同じロジックが他のファイルにコピーされて存在することに気づかない） |
| 将来コスト         | この設計のまま拡張したときに破綻しないか。車輪の再発明になっていないか                                                                                                                                                                                |

## フル方式: 4レンズ並列 + 検証

差分の影響範囲が広いとき用。どちらもStep 1で集めた周辺コンテキストを各エージェントに渡し、「そのレンズだけ見よ」と指示する点は共通。

### 基本形: `Agent` ツールでの並列 dispatch（どの環境でも使える）

`Agent` ツールを1つの応答の中で複数回呼び出すと並列実行される（`superpowers:dispatching-parallel-agents` と同じ考え方）。

```
Agent(仕様面担当): "差分: <diff>\n周辺コンテキスト: <Step1の要約>\n狙い: <基準線>\n\nこの差分が狙い通りに実装されているか、仕様面だけをレビューせよ。コードの正しさ・コード品質・設計は見なくてよい。"
Agent(正しさ担当): "差分: <diff>\n周辺コンテキスト: <Step1の要約>\n\nコードの正しさ(バグ・契約整合・エラーハンドリング・テスト)だけをレビューせよ。呼び出し元の期待と食い違う変更がないか周辺コンテキストと突き合わせること。動作に影響しない純粋なスタイルの指摘は対象外。"
Agent(品質担当): "差分: <diff>\n\nこの差分単体のコード品質(命名・制御フローの複雑さ・重複・抽象化の粒度・型設計)だけをレビューせよ。コメント・docstringの可読性は対象外(pr-first-reader-checkの担当)。既存コードとの整合性は見なくてよい。バグが無くマージ可能でも、可読性・複雑さの指摘は別立てで書くこと。"
Agent(設計担当): "差分: <diff>\n周辺コンテキスト: <Step1の要約>\n\n全体設計(アーキテクチャ整合・類似実装との一貫性・取りこぼし)だけをレビューせよ。特に「同じ修正が必要な箇所が他にもあるのに一部しか直っていないか」を周辺コンテキストの類似実装リストと突き合わせて確認すること。"
```

4つとも同一メッセージ内で呼び出す。返ってきた指摘のうち Important 相当以上は、Step 3 のとおり別の `Agent` 呼び出しで「実際にファイルを読んで裏付けが取れるか」を検証させ、取れなかったものは落とす。

### 任意: `Workflow` ツールが使える場合の自動化雛形

`Workflow` ツールはメインの会話セッションでは使えるが、**自分がサブエージェントとして起動されている場合は使えないことがある**。使う前に `ToolSearch` 等で存在を確認し、無ければ上の `Agent` ツール並列 dispatch にフォールバックする。そのままコピペするのではなく、対象に合わせて調整すること。

```js
export const meta = {
  name: 'pr-deep-review-fanout',
  description:
    '差分を周辺コンテキスト込みで仕様/正しさ/コード品質/設計の4レンズで深掘りレビューする',
  phases: [{ title: 'Context' }, { title: 'Review' }, { title: 'Verify' }],
};

// args: { target: 'git diff origin/<default-branch>...HEAD の説明 or PR番号', intent: 'イシュー/PRの狙い(基準線)' }

phase('Context');
const context = await agent(
  `${args.target} の差分を対象に、以下を調べて構造化して返せ:\n` +
    `1. 変更されたシンボルごとの呼び出し元一覧(grep結果)\n` +
    `2. 同種の処理をしている既存の類似実装ファイル\n` +
    `3. 対応するテストファイルの有無と内容\n` +
    `4. 変更した値が下流のどのモジュールで使われるか\n` +
    `生ファイル内容の丸ごと引用はせず、パスと要点だけ返すこと。`,
  { phase: 'Context', model: 'sonnet' },
);

const LENSES = [
  {
    key: 'spec',
    prompt: `狙い: ${args.intent}\n\n差分と周辺コンテキスト:\n${context}\n\nこの差分が狙い通りに実装されているか、仕様面(要求充足・暗黙の仕様との整合)だけをレビューせよ。コードの正しさ・コード品質・設計は見なくてよい。`,
  },
  {
    key: 'correctness',
    prompt: `差分と周辺コンテキスト:\n${context}\n\nコードの正しさ(バグ・契約整合・エラーハンドリング・テスト)だけをレビューせよ。呼び出し元の期待と食い違う変更がないか周辺コンテキストと突き合わせること。動作に影響しない純粋なスタイルの指摘は対象外。`,
  },
  {
    key: 'quality',
    prompt: `差分:\n${context}\n\nこの差分単体のコード品質(命名・制御フローの複雑さ・重複・抽象化の粒度・型設計)だけをレビューせよ。コメント・docstringの可読性は対象外(pr-first-reader-checkの担当)。既存コードとの整合性は見なくてよい。バグが無くマージ可能でも、可読性・複雑さの指摘は別立てで書くこと。`,
  },
  {
    key: 'design',
    prompt: `差分と周辺コンテキスト:\n${context}\n\n全体設計(アーキテクチャ整合・類似実装との一貫性・取りこぼし)だけをレビューせよ。特に「同じ修正が必要な箇所が他にもあるのに一部しか直っていないか」を周辺コンテキストの類似実装リストと突き合わせて確認すること。`,
  },
];

const FINDINGS_SCHEMA = {
  type: 'object',
  properties: {
    findings: {
      type: 'array',
      items: {
        type: 'object',
        properties: {
          file: { type: 'string' },
          line: { type: 'number' },
          summary: { type: 'string' },
          failure_scenario: { type: 'string' },
          severity: { type: 'string', enum: ['Critical', 'Important', 'Minor'] },
        },
        required: ['file', 'summary', 'failure_scenario', 'severity'],
      },
    },
  },
  required: ['findings'],
};

const VERDICT_SCHEMA = {
  type: 'object',
  properties: {
    verdict: { type: 'string', enum: ['CONFIRMED', 'PLAUSIBLE', 'REFUTED'] },
    reason: { type: 'string' },
  },
  required: ['verdict', 'reason'],
};

phase('Review');
const reviewed = await pipeline(
  LENSES,
  (l) =>
    agent(l.prompt, {
      label: `review:${l.key}`,
      phase: 'Review',
      model: 'sonnet',
      schema: FINDINGS_SCHEMA,
    }).then((r) => ({ lens: l.key, findings: r?.findings ?? [] })),
  // pipeline/parallel の内側では、グローバルな phase('Verify') ではなく
  // 呼び出しごとの opts.phase で 'Verify' グループに割り当てる
  // (レンズごとに並列で進むため、グローバル phase() の呼び出し順に依存できない)
  (r) =>
    parallel(
      r.findings.map(
        (f) => () =>
          agent(
            `この指摘を敵対的に検証せよ。実際に該当ファイルを開いて裏付けを取ること。裏付けが取れなければ REFUTED。\n指摘: ${JSON.stringify(f)}`,
            // 複数票の多数決ではなく1指摘につき1エージェントが単独で CONFIRMED / PLAUSIBLE / REFUTED を決める
            // 最終ジャッジなので、model を省略してメインセッションのモデルの継承を狙う
            // (subagent-model-policy.md の敵対的検証の最終ジャッジに該当する例外)。
            // 実際に動くモデルは /tasks で確認する。
            { label: `verify:${f.file}`, phase: 'Verify', schema: VERDICT_SCHEMA },
          ).then((v) => ({ ...f, lens: r.lens, verdict: v?.verdict, verdictReason: v?.reason })),
      ),
    ),
);

const confirmed = reviewed
  .flat()
  .filter(Boolean)
  .filter((f) => f.verdict !== 'REFUTED');
return { confirmed };
```

出力は `confirmed` の一覧を Step 4 の出力フォーマット（レンズ別テーブル）に整形する。
