# PRD レビュー基準詳細

良質な PRD に共通するパターンから抽出したレビュー基準。

## 1. ロジックの一貫性

### チェック項目

- **Why → What → How → 計測 の縦串が通っているか**
  - 背景で述べた課題が、仮説で解決方法として言語化されているか
  - 仮説が提案のサマリ（What）に対応しているか
  - 提案のサマリが機能要件に分解されているか
  - 計測指標が仮説の検証に直結しているか

- **ビジネス指標への接続**
  - この施策がチーム目標（アクティベーション率, 商談化数等）にどう繋がるかのロジックが明文化されているか
  - 中間ステップが省略されていないか（例: 「不安解消 → ??? → 目標指標」のような飛躍）

- **参考: 良いロジックの例**
  ```
  背景: 設定を初期値のまま使っているユーザーが多い
  仮説: 変更後の見え方が分かれば、ユーザーは自分に合う設定へ調整する
  What: 設定変更のプレビューを、限定公開のテスト参加者へ出す
  計測: 設定を変更したユーザー数（ファネル分解つき）
  判定: 検証 → 本実装、棄却 → 方向転換
  ```

### よくある問題

- ユーザー価値の話とビジネス指標の話が別々に書かれていて繋がっていない
- 「〜が増えるはず」で終わっていて、なぜ増えるかのメカニズムが書かれていない
- 中間ステップの省略（ユーザーの行動変容 → ビジネス指標 の間の「なぜそう動くか」がない）

## 2. 仮説の明確さ

### チェック項目

- **検証可能な形で書かれているか**
  - 「〜すれば〜になる」という if-then 形式になっているか
  - 検証された場合と棄却された場合の次のアクションが書かれているか

- **仮説の前提が明示されているか**
  - この仮説が成り立つために必要な前提条件が書かれているか
  - 前提が崩れた場合にどうなるかが意識されているか

- **参考: 良い仮説の例**
  ```
  仮説: 継続利用しているが設定を変えていないユーザーが、変更後の見え方のプレビューを
        きっかけに、自分に合う設定へ調整する。
  検証された場合: プレビューの本実装を進める
  棄却された場合: プレビューで設定変更を促す方向を諦める
  ```

### よくある問題

- 仮説が抽象的すぎて検証方法が導けない
- 複数の仮説が混在していて、どれを検証しているか不明確
- 「〜だと思う」「〜のはず」のような確信度が不明な記述

## 3. 対象ユーザーとスコープ

### チェック項目

- **対象ユーザーの規模感があるか**
  - 「〜な人」だけでなく、何人いるか（推定でもよい）が書かれているか
  - アクティブ率など、実際にリーチできる人数の見積もりがあるか

- **スコープの境界が明確か**
  - 「今回やること」と「今回やらないこと」が節として明示されているか
  - なぜやらないかの理由があるとなおよい

- **参考: 良いスコープの例**
  ```
  ## 今回対応しないこと
  * 保存済みリストの絞り込み:
      * 特定の保存済みリストを除外する機能は、今回は対応しない。
      * 特定の保存済みリストのみを検索対象とする機能も、今回は対応しない。
  ```

### よくある問題

- 対象ユーザーが「全ユーザー」のような曖昧な定義
- 規模感がゼロ（何人が対象か不明）
- スコープが無限に広い（境界がない）

## 4. 背景のエビデンス

### チェック項目

- **事前検証の結果が参照されているか**
  - ユーザーインタビュー、プロトタイプテスト、データ分析の結果が引用されているか
  - 「〜だと思う」ではなく「〜という結果が出た」で書かれているか

- **データの裏付けがあるか**
  - 規模感、割合、トレンドなどの数値が含まれているか
  - データの出典（分析クエリ、社内Wikiリンク等）が明記されているか

- **参考: 良い背景の例**
  - ユーザーテスト3回分の結果を要約して引用
  - 各テストで何がわかったかを明記
  - テスト結果を受けた方針転換の理由を説明

### よくある問題

- 課題認識が主観のみ（「〜だと感じている」）
- 先行事例や既存データへの参照がない
- 競合分析が「〜している」のみで具体性がない

## 5. 計測指標の具体性

### チェック項目

- **指標がファネル分解されているか**
  - 最終指標だけでなく、中間指標が定義されているか
  - ファネルの各段階で何を見るかが明確か

- **参考: 良い計測の例（ファネル分解）**

  ```
  * 期間内の対象画面の閲覧数
      * うち導線をクリックしたユーザー数
          * うちクリック時点で未設定だったユーザーの割合
              * うち設定を完了したユーザーの割合
  ```

- **参考: 良い計測の例（利用・行動・精度の3層）**
  ```
  機能利用率: 各オプションの1日あたり利用回数、利用アカウント数、全利用に対する利用率
  行動量: その機能を経由しなければ起こりえない操作の発生数
  精度: 提示した結果に対する反応率
  ```

### よくある問題

- 「目標指標の増加」だけで、何をもって増加とするかが不明
- 指標はあるが目標値がない
- 施策の効果と他要因を分離する方法が考慮されていない

## 6. 機能要件の具体性

### チェック項目

- **優先度がついているか**
  - P1/P2/P3 等の優先度で分類されているか
  - 各優先度の判断基準が明確か

- **各機能の「何をするか」が具体的か**
  - 入力・処理・出力が読み取れるか
  - ユーザーの操作フローが想像できるか

- **参考: 良い機能要件の例**
  - P1/P2/P4 で分類
  - 各機能に技術的要件が対応
  - デザインモックとの対応が明確

### よくある問題

- 機能名だけで中身がない
- 優先度がついていない
- 技術的な実現可能性への言及がない

## 7. 考慮すべき点と意思決定ログ

### チェック項目

- **意思決定が記録されているか**
  - 複数の選択肢を検討した跡があるか
  - なぜその選択をしたかの理由が書かれているか

- **参考: 良い意思決定ログの例**
  - 「仕様上の論点」セクションで複数の論点をそれぞれ記録
  - 各論点に選択肢（案1〜4）と pros/cons を列挙
  - 決定事項を見出しに含めている（例: 「→ 案3とする」）

- **考慮すべき観点**
  - Legal（法令、利用規約）
  - カスタマーサクセス（法人向け運用への影響）
  - エンドユーザーサポート（個人向け運用への影響）
  - マーケ（拡散、広告、キャンペーン）
  - リリースマネジメント
  - ユーザー行動分析（計測データ）
  - プラットフォームの健全性・不正利用対策

### よくある問題

- 決定事項だけが書かれていて、検討過程がない
- 「〜とする」だけで理由がない
- Legal/CS/マーケ等の観点が完全に欠落

## 8. 読みやすさ・構造

### チェック項目

- **初見の人が読んで理解できるか**
  - 専門用語や社内用語に説明があるか（Key Terms セクション）
  - 情報の重複がないか
  - 各セクション間で矛盾がないか

- **構造が論理的か**
  - Why → What → How の順序で読めるか
  - 長い議論は折りたたみ（details タグ）で整理されているか
  - 図やモックが適切に配置されているか

### よくある問題

- 同じ情報が複数箇所に散在している
- セクション間の論理的なつながりが不明
- 読者の前提知識に依存しすぎている
