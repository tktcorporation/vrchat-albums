# PRD レビュースキル

PRD を体系的にレビューし、改善ポイントを特定するスキル。
良質な PRD に共通するパターンを基準に評価する。

## レビュー対象の取得

1. 社内Wiki記事番号が指定された場合: 該当ツールの取得コマンド/APIでpullしてローカルに取得
2. ローカルファイルが指定された場合: そのまま読み込み
3. 指定がない場合: ユーザーにどのPRDをレビューするか確認

## レビュー手順

### Step 1: 全文通読

PRD全体を読み、以下の第一印象を記録する:

- このPRDは何を実現しようとしているか（1文で）
- 読み終えた時点で不明な点は何か
- 直感的に「弱い」と感じるセクションはどこか

### Step 2: 8観点での評価

`references/review-criteria.md` の詳細基準に基づき、以下の8観点で評価する。

| #   | 観点                       | 評価のポイント                                       |
| --- | -------------------------- | ---------------------------------------------------- |
| 1   | **ロジックの一貫性**       | Why → What → How → 計測 の縦串。ビジネス指標への接続 |
| 2   | **仮説の明確さ**           | if-then形式、検証/棄却時の次アクション、前提条件     |
| 3   | **対象ユーザーとスコープ** | 規模感の有無、「やらないこと」の明示                 |
| 4   | **背景のエビデンス**       | 事前検証・データ・先行事例の参照                     |
| 5   | **計測指標の具体性**       | ファネル分解、目標値、効果の分離方法                 |
| 6   | **機能要件の具体性**       | 優先度、操作フロー、技術的実現可能性                 |
| 7   | **意思決定ログ**           | 選択肢の検討過程、決定理由、Legal/CS等の観点         |
| 8   | **読みやすさ・構造**       | 初見理解性、重複の有無、情報の流れ                   |

### Step 3: レビュー結果の出力

以下のフォーマットで出力する:

```markdown
## PRDレビュー: [PRDタイトル]

### サマリ

[このPRDが何を実現しようとしていて、全体としての完成度はどうか。2-3文]

### 評価

| 観点             | 評価    | 概要   |
| ---------------- | ------- | ------ |
| ロジックの一貫性 | ◎/○/△/× | [一言] |
| 仮説の明確さ     | ◎/○/△/× | [一言] |
| ...              | ...     | ...    |

### 良い点

[箇条書き。PRDの強みを具体的に]

### 改善が必要な点（優先度順）

[優先度の高い順に。各項目に「なぜ問題か」「どう改善するか」を含める]

### 具体的な改善提案

[最も重要な2-3点について、具体的にどう書き換えるかの提案]
```

## 評価基準

各観点の評価は以下の基準で行う:

- **◎**: 後述の「良質な PRD に共通する特徴」を満たす。改善の余地がほぼない
- **○**: 必要な情報はあるが、より良くできる余地がある
- **△**: 重要な情報が不足している。読み手に疑問が残る
- **×**: セクション自体がないか、あっても機能していない

## レビュー時の原則

### 書くべき情報 vs 書かなくてよい情報

**書くべき情報:**

- この施策がなぜチーム目標を進めるのか（ロジックチェーン）
- 検証したい仮説が何か（if-then + 検証/棄却時のアクション）
- 対象ユーザーの規模感（推定でよい）
- 意思決定の背景（なぜこの選択肢を選んだか）
- 「やらないこと」の明示

**書かなくてよい情報:**

- テンプレートのプロンプトコメント（`> MVPで検証したい仮説。` 等）— PRD完成時に削除する
- 自明な定義の繰り返し
- 他のドキュメントと完全に重複する内容（リンクで参照すれば十分）
- 決まっていないことの推測（[TBD] にすべき）

### faithful-doc-writing との連携

レビュー結果で「この情報が足りない」と指摘する場合:

- その情報をAIが推測で埋めることは提案しない
- 「ユーザーに確認すべき質問」として提示する
- ユーザーが答えた内容のみをPRDに反映する

## 参考リソース

### レビュー基準の詳細

- **`references/review-criteria.md`** — 8観点の詳細な基準、良い例・悪い例、よくある問題パターン

### 良質な PRD に共通する特徴

- 短くまとまっていて、やること / やらないことの境界がはっきりしている
- 仮説が if-then で書かれ、検証・棄却それぞれの次アクションまで決まっている
- 効果を測る指標がファネルまで分解され、事前検証やテスト設計が添えられている
- 選択肢の検討過程と決定理由が意思決定ログとして残っている

評価の基準にする既存 PRD がプロジェクトにあるなら、それを先に読んで水準を合わせる。
