# Functional DDD — ドメイン知識をコードに埋め込む

ドメイン知識が**ドキュメント・コメント・人間の記憶**にしか無い状態を、**型とデータ**へ移す。クラスにメソッドを生やす方向ではなく、データと関数を単方向に結合する形で行う。

読みやすさは、オブジェクトに振る舞いを持たせることではなく、**モジュール境界が概念と一致していること**で担保する。

## このスキルの役割と境界

- **担うのは「知識をどこに、どんな形で置くか」の判断** — 型の設計、モジュールの切り方、何をコードに移し何をドキュメントに残すか
- **前提として別ルールがある** — 「不正な状態を作れない型設計」は `robustness.md`、「失敗をどう表現するか」は `error-handling.md` が SSOT。本スキルはそれらを再説明せず、**その上で知識の置き場所を決める**
- **診断が先、実装は後** — まず下の smell を探す。smell が無ければ何も変えない

## 診断 — ドメイン知識がコードから抜けている兆候

コードを読んで次を探す。1 つでも当たれば、その概念は「コードに書かれていない」。

| 兆候                                                                                                         | 何が起きているか                                                       |
| ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| **ルールがドキュメントにしか無い** — 状態遷移表・不変条件・制約の一覧が `.md` にあり、コードには断片しか無い | 知識とコードが二重管理。ドキュメントが腐ると誰も気づけない             |
| **同じ条件式が複数箇所に重複している**                                                                       | その式が表すルールに名前が付いていない。1 箇所直し忘れても検知できない |
| **状態を boolean フラグや nullable の組み合わせで持っている**                                                | ありえない組み合わせが型として作れる（`robustness.md` 原則 1）         |
| **コメントが条件式を自然言語へ翻訳している**                                                                 | 読み手が式を意味へ変換しないと読めない。翻訳をコードにする余地がある   |
| **同じ型のプリミティブが別の意味で飛び交う**                                                                 | 取り違えをコンパイラが助けられない（`robustness.md` 原則 4）           |
| **「〜のときは〜できない」がハンドラや UI に散っている**                                                     | ドメインのルールが呼び出し側に漏れ出している                           |
| **モジュールが技術的役割で切られている**（`utils/` `services/` `helpers/`）                                  | 1 つの概念が複数ファイルに散り、モジュール名から中身を推測できない     |
| **ファイルが「〜に必要な関数の置き場」になっている**                                                         | 凝集の軸が概念ではなく用途。肥大化しても分割の切れ目が見つからない     |

## 4 つの層に切り分けて考える

「ドメインモデリングしたい」という要望は、たいてい次のどれか 1 つの話に落ちる。**どの層の問題かを先に決める**と、打ち手が一意に決まる。

| 層       | 手法                              | 何をするか                                                         |
| -------- | --------------------------------- | ------------------------------------------------------------------ |
| **境界** | Parse, don't validate             | 外部入力を検証と同時に精密な型へ変換し、通過後は再検証を不要にする |
| **コア** | ADT + 全域関数                    | 排他的な状態を tagged union で表し、処理を網羅的な全域関数で書く   |
| **配置** | Functional Core, Imperative Shell | 副作用を外殻へ押し出し、中心を純粋関数だけにする                   |
| **依存** | Port & Adapter                    | 外部依存をインターフェースとして宣言し、実装を注入する             |

境界とコアは `robustness.md` が型設計として、配置と依存はモジュール構成として扱う。

## OOP の DDD からの読み替え

DDD の戦術パターン名そのものにこだわる必要はない。関数型では次に対応する。

| OOP の DDD                          | 関数型での形                                                               |
| ----------------------------------- | -------------------------------------------------------------------------- |
| Aggregate（状態を守るオブジェクト） | **状態遷移を行う純粋関数の集合**。トランザクション境界の管理は呼び出し側へ |
| Value Object（振る舞いを持つ値）    | **branded type**。振る舞いは持たせず、その型を受け取る関数として外に出す   |
| Domain Service                      | **純粋関数**。副作用が要るものは外殻へ                                     |
| Repository                          | **Port として宣言したインターフェース** + 実装の注入                       |
| Entity のメソッド                   | データと関数の単方向結合（`entity.doX()` ではなく `doX(entity)`）          |

エンティティが自身の振る舞いを持てないぶん、**知識はモジュールの構成と型の形で表現する**。

## モジュールは概念で切る

技術的役割ではなく、ドメイン概念でトップレベルを切る。モジュール名がドメイン用語になっていれば、中身を読まなくても責務が分かる。

```
<概念>/
  core    — 純粋関数 + ADT（状態遷移・計算・判定）
  schema  — 境界のパース
  port    — 外部依存のインターフェース宣言
  layer   — Port の実装（永続化・外部 API）
  index   — 公開 API。他モジュールはここだけを参照する
```

すべてを揃える必要は無い。**純粋なコアだけを切り出す**段階から始めてよく、Port が 1 つも無いモジュールも正当。

分割の判断基準は「**このファイルの名前を見て、中に何があるか言えるか**」。言えないなら概念で切れていない。

## 実行可能な仕様にする

ドキュメントにしか無いルールをコードへ移すときの型。散らばった条件式を「**単一の宣言 → そこからの導出**」に組み替える。

1. **状態に名前を与える** — nullable の組み合わせや文字列を、tagged union として定義する
2. **その値をパースする全域関数を 1 つ置く** — 生データの解釈をここに閉じ、以降は状態名で語る
3. **ルールをデータとして宣言する** — 遷移・許可・制約の一覧を、実行可能な定義として書く
4. **実際の条件式をその定義から導出する** — 重複していた式を、宣言から生成された 1 つの経路に置き換える
5. **不変条件をテストで検証する** — 「この状態は終端」「この経路だけが逆行できる」など、定義を走査して機械的に検査する

5 で確かめられるのは宣言そのものの整合まで。**宣言どおりに動く実装が、到達しうる全ての状態で不変条件を保つか**は別の問題で、状態と操作の組み合わせが増えるとテストでは経路を書き切れない。そこまで確かめたいときは、状態空間を探索して反例を探す仕様モデルの手法がある。プロジェクトに該当するスキルがあればそれに従う。

ここまでやると、ドキュメントの表は**コードが SSOT**になる。`.md` には**なぜそのルールなのか**という WHY だけを残し、表そのものは消してコードを参照させる（`doc-placement.md`）。

### 宣言が本当に駆動しているか確かめる

宣言をデータとして書いただけでは、それが SSOT になったとは言えない。**その宣言を書き換えたとき、実際の挙動が変わるか、実挙動を観測しているテストが落ちるか**を確かめる。どちらも起きないなら、その宣言は何も駆動していない飾りで、実装と静かに食い違ったまま気付けない。

確かめ方は、宣言の値を意図的に誤った値へ書き換え、テストが落ちることを見てから戻す。**証拠になるのは、宣言とは独立に実際の書き込みや出力を観測しているテストだけ**。宣言そのものを走査する不変条件のテストは、実装が別の値を使い続けていても宣言を変えれば落ちるので、駆動の証拠にならない。ここを取り違えると、飾りを SSOT と誤認する。

落ちないなら、次のどちらかで実装と結ぶ。

- **導出する** — 宣言から実際の値を機械的に組み立てる。可能ならこれが最も強い
- **突き合わせる** — 実際の挙動を動かして観測し、宣言と一致することをテストで固定する。導出できない形（組み立て方が対象ごとに揃わない等）はこちら

宣言の一部だけが駆動していて残りが飾り、という状態が最も危ない。飾りの側も「定義されているのだから正しい」と読まれるため、宣言全体の信頼が実態より高く見積もられる。

### 移動元を指す参照を付け替える

情報をドキュメントからコードへ移したら、**移す前の場所を指している参照を全部探して付け替える**。移動元のファイルだけを見ていると、別の場所から「詳細はあちらにある」と案内している箇所が取り残され、案内された先に情報が無い状態になる。

取り残された参照は、変更したファイルを眺めても見つからない。移した情報の名前でリポジトリ全体を検索する。

## 適用しない判断

過剰設計を避けるため、次の場合は**何もしない**のが正しい。

- **状態が 1 つしか無い / 遷移が無い** — 単純な CRUD に Aggregate 相当の構造を持ち込まない
- **ルールが 1 箇所にしか無く、重複していない** — 抽象化の対象がまだ存在しない
- **概念がまだ固まっていない** — 境界を引くのが早すぎると、間違った境界を跨ぐコストを払い続ける
- **導出の仕組みが、元の条件式より読みにくい** — 目的は可読性。手段が目的を殺したら本末転倒

**判断に迷ったら、まず名前を付けるだけで止める。** 型を作らなくても、条件式に名前の付いた定数を与えるだけで smell が消えることは多い。

## セルフチェック

書き終えたら次を確認する。

1. **知識の所在** — このモジュールの外を読まないと分からないルールが残っていないか
2. **重複** — 同じルールを表す式が 2 箇所以上に無いか
3. **命名** — モジュール名・型名がドメイン用語になっているか（技術用語で埋まっていないか）
4. **不正状態** — ありえない組み合わせが型として作れないか（`robustness.md`）
5. **純粋性** — コアに I/O が混ざっていないか
6. **ドキュメント** — `.md` に残したのは WHY だけか。コードが語れる WHAT を転記していないか
7. **駆動** — 宣言を誤った値に変えたら、実挙動を観測しているテストが落ちるか。宣言を走査するだけのテストが落ちても証拠にならない
8. **参照** — 元の場所を指していた箇所が、移した先を指すよう直っているか
9. **やりすぎ** — 導出の仕組みが元のコードより読みにくくなっていないか

## 用語 — 相手に伝えるときの名前

議論や依頼で使うと一発で通る呼び名。

| 言いたいこと                               | 通る名前                                    |
| ------------------------------------------ | ------------------------------------------- |
| 全体の方針                                 | 関数型DDD / Domain Modeling Made Functional |
| ありえない状態を型で作れなくする           | Make illegal states unrepresentable         |
| 境界で検証して型に事実を持たせる           | Parse, don't validate                       |
| 副作用を外殻へ、中心を純粋に               | Functional Core, Imperative Shell           |
| 状態と選択肢を代数的データ型で表す         | ADT ベースのドメインモデリング              |
| ドキュメントの仕様をコードで検証可能にする | 実行可能な仕様 (executable specification)   |

「関数型DDDで書きたい。エンティティにメソッドを生やすのではなく、ADT と純粋関数で状態遷移を表現したい」と言うと、意図が正確に伝わる。後半が無いと、DDD という語からクラスベースの実装が提案されやすい。

## 実現手段はプロジェクトの規約に従う

同じ設計を実現する道具は言語とライブラリで変わる。網羅的な分岐、境界のパース、名目的な型の区別、依存の注入は、どれも複数の実現手段がある。プロジェクトのコード規約に定めがあればそれに従い、無ければ既存コードで多数派の手段に合わせる。`.claude/rules/project/` 配下に該当ルールがあれば、そちらを確認して従う。

**道具の選択より、どの層の問題を解こうとしているかを先に決めることの方が効く。** 手段が決まっていても、境界の話とコアの話を取り違えていれば設計は良くならない。
