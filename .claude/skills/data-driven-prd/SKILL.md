# データ駆動PRD作成スキル

## このスキルが解決する問題

PRD作成時、2つの問題が起きやすい:

1. **AIが推測で書いてしまう**: ユーザーが言ってないことを「〜と考えられます」で埋める。
   後から「違う、それはそういうことじゃない」と修正コストが発生する。
2. **データなしで仮説を書く**: 「効果があった」と書くが、具体的な数字や比較がない。
   説得力のないPRDになる。

このスキルは、faithful-doc-writing の忠実記録原則 + データ収集・分析フェーズで
両方の問題を解決する。

---

## 原則

### faithful-doc-writing 原則（継承）

1. **ユーザーが言ったことだけを書く** — 言い換えは最小限、推測で情報を足さない
2. **言ってないことは [TBD] にする** — 空欄をそれっぽく埋めない
3. **不足を埋めるには質問する** — 推測ではなくユーザーに聞く

### データ分析の原則（追加）

4. **分析はしてよい、解釈は確認してから書く**
   - データの差分計算、比較、トレンド把握 → そのまま書いてよい
   - ユーザーの発言に解釈を加える → 書かない
   - 「こういうパターンがある」「こう読み取れる」等の解釈 → ユーザーに
     「こういう理解であってますか？」と確認してからPRDに書く
   - ユーザーが言ってない結論 → 書かない

5. **数字の出典を明確にする**
   - PRDに書く数字は、どのデータソース・どのクエリから来たか追跡できるようにする
   - ユーザーの発言した数字とデータから取得した数字を混同しない

6. **データとユーザーの主張が一致しない場合は報告する**
   - ユーザーが「Xが一番増えた」と言ったが、データではYの方が大きい場合
   - PRDに勝手に修正して書かず、会話でユーザーに報告する
   - ユーザーの判断を待ってからPRDに反映する

## ワークフロー

### Phase 1: ヒアリング & PRD骨格作成

faithful-doc-writing スキルのワークフローに従う。

1. ユーザーの話を聞く
2. 発言を「明言された事実 / 示唆された方向性 / 言及されていない項目」に分類
3. PRDテンプレートに沿って骨格を作成
4. 言及なし項目は `[TBD: 説明]` にする
5. 参考になる既存PRDがあれば社内ドキュメントツールから取得してフォーマットを合わせる

**出力**: PRD下書き（[TBD] 多数の状態）

### Phase 2: データ収集

PRDの [TBD] 項目やユーザーの仮説を見て、必要なデータを集める。

1. **必要なデータの特定**: PRDのどの [TBD] をどのデータソースで埋められるか整理する
2. **データ収集の実行**: 以下のデータソースから情報を取得する
3. **SQLクエリが必要な場合**: クエリを作成し、ユーザーにBIツール上で実行してもらう
4. **生データの保存**: 取得したデータは `drafts/` 等にTSV/SQLとして保存する

#### データソースと用途

| データソース                              | 用途                                       | 取得方法                                              |
| ----------------------------------------- | ------------------------------------------ | ----------------------------------------------------- |
| **メール配信ツールの配信履歴**            | 施策のリリース時期、通知数、開封率、CTR    | エクスポートしたTSV/CSVを読み取り、施策名・日付で検索 |
| **BIツール／SQL実行環境（コホート分析）** | 新規ユーザーを排除した施策効果の測定       | SQLクエリを作成→ユーザーが実行→結果を読み取り         |
| **BIツール／SQL実行環境（全体トレンド）** | ユーザー行動の時系列推移、ベースライン把握 | 同上                                                  |
| **GitHub PR/Issue**                       | 施策の具体的な変更内容、バージョン情報     | `gh pr list`, `gh issue list` で検索                  |
| **社内ドキュメントツールの記事**          | 過去の分析結果、関連PRD                    | 自社の取得スクリプト/API経由で取得                    |
| **その他**                                | ユーザーが指定するデータソース             | 都度対応                                              |

#### メール配信ツール検索のコツ

- 施策名、バージョン番号、機能名でgrep検索する
- ニュースレター（NL）と個別通知メールを区別する（個別通知のCTRが施策効果の目安）
- 通知数が数百通以下のものはテスト配信やインタビュー依頼の可能性がある
- **送信日の確認が重要**: 配信ツール上の表示名に含まれる日付（例: "20260213ニュースレター"）は
  作成日であり、実際の送信日と異なる場合がある。エクスポートした送信日列を必ず確認すること

#### コホート分析のコツ

- 「固定コホート」= ある時点で存在したユーザーのみを追跡（新規登録の影響を排除）
- 施策のない週（ベースライン）の増分を確認し、施策ありの週と比較する
- 全体トレンドは新規ユーザーを含むため、コホートとの差が「新規ユーザーの寄与分」

#### GitHub 検索のコツ

- バージョン番号（v1.4.0 等）でPRを検索
- リリースPR（Release YYYYMMDD...）からデプロイ日を特定
- PRのタイトルと本文から「ユーザー向けにどういう変更だったか」を1-2行で要約

**出力**: 収集したデータの一覧（生データ + 保存先パス）

#### 施策効果テーブルの生成（自動化スクリプト）

施策ごとの全体/コホート週増分テーブルを作る場合、手作業での週アラインメントはミスしやすい。
自組織に同種の自動化スクリプトがあれば使う（本スキル自体はスクリプトを同梱しない）。

**手順:**

1. **施策定義TSVを作成する**（これが人間の判断が必要な部分）:
   - メール配信履歴・GitHub PR/Issue から施策を特定する
   - 各施策の送信日、個別通知数、★フラグを記録する
   - 同じテーブル行にまとめる送信は同じ `row` 番号にする（NLと個別メールが別日など）
   - 配信ツールの表示名に含まれる日付（作成日）と実際の送信日が異なる場合があるので、
     送信日列を確認すること

   ```tsv
   row	send_date	name	notification_count	star
   1	2025/01/16	OrderRouter機能 v2.0 公開
   1	2025/01/21	OrderRouter機能 v2.0 公開	1400
   2	2025/02/13	OrderRouter機能 v2.1.0	1350
   ```

2. **スクリプトを実行する**（例。自組織の自動化スクリプトに合わせて読み替える）:

   ```bash
   python3 scripts/campaign_effect_table.py \
     --campaigns drafts/campaigns_XXXX.tsv \
     --overall drafts/query_overall_trend.tsv \
     --cohort path/to/query_cohort_timeseries.tsv \
     --bold-threshold 20
   ```

3. **出力を確認する**:
   - 警告（同一週重複、金曜送信）が出たら内容を確認してPRDに注釈を追加する
   - テーブルをPRDにそのままコピーできる

**スクリプトが自動で行うこと:**

- 送信日 → 月曜始まり週へのマッピング
- 全体/コホートTSVから該当週の増分を取得
- 同一週に複数施策がある場合の検出・警告
- 金曜送信の短い反映期間の警告
- 太字の自動適用（コホート増分がしきい値以上）

**人間（またはClaude）が判断する部分:**

- どの配信メールがどの施策に対応するか
- 複数メールを1行にまとめるかどうか（row番号の付け方）
- 施策名の表記（バージョン番号、内容の要約）
- ★フラグの判断（アウトプット加味施策かどうか等）

### Phase 3: データ分析 & PRD反映

1. **データの整理**: 収集したデータを表・時系列に整理する
2. **分析**: 差分計算、比較、トレンド把握を行う
3. **ユーザーの主張との照合**: データがユーザーの仮説を支持するか確認する
   - 支持する場合 → データをPRDに反映
   - 支持しない場合 → **PRDに勝手に修正して書かない**。
     会話で「データを見ると〜ですが、こちらの理解であってますか？」と報告する
4. **PRDへの反映**: データから直接読み取れる事実のみをPRDに書く

#### 書いてよいもの

- データの数値（ユーザー数、増分、通知数、CTR等）
- データの比較（「Aは+38、Bは+50」）
- ベースラインとの差（「無施策期間は+0〜6、施策後は+38」）
- バージョン番号と内容の対応（「v1.4.0 = OrderRouter機能反映」）
- ユーザーがそのまま言ったこと

#### 書いてはいけないもの

- 「〜と考えられる」「〜のパターンがある」等のAIの解釈（確認なしで）
- ユーザーが言ってない結論（「最も効果的だったのは〜」等）
- ユーザーの発言の言い換え・補足
- 施策の分類・カテゴリ付け（ユーザーが分類していない場合）

**出力**: データ反映済みPRD

### Phase 4: セルフチェック & 仕上げ

#### faithful-doc-writing チェック（継承）

1. **出典チェック**: 書いた全ての事実・数字について「ユーザーが言った」か
   「データソースXから取得した」と指し示せるか？
2. **言い換えチェック**: ユーザーの言葉を大きく変えていないか？
3. **追加チェック**: ユーザーが言っていない補足・注意・提案が紛れ込んでいないか？
4. **TBD チェック**: 全項目について、情報があるかTBDかが明確か？

#### データ分析チェック（追加）

5. **数字の出典チェック**: PRDの数字がどのクエリ・どのファイルから来たか追跡できるか？
6. **主張-データ整合チェック**: ユーザーの主張とデータが矛盾している箇所はないか？
   矛盾があればユーザーに報告したか？
7. **AI解釈チェック**: 「読み取れること」「ポイント」「パターン」等の
   AI解釈がPRDにラベルなしで混入していないか？
8. **分類チェック**: ユーザーが分類していない施策にAIが勝手にカテゴリを
   つけていないか？（例: 「パワーユーザー向け施策」とユーザーが言っていないものに
   そのラベルをつける）

#### 仕上げ

- 残存 [TBD] リストと質問リストを提示
- 社内ドキュメントツールに反映する

## 禁止事項

| やりがちなこと                                 | なぜダメか                   | 実例                                                   |
| ---------------------------------------------- | ---------------------------- | ------------------------------------------------------ |
| ユーザーの発言を「より良く」言い換える         | 意図が変わるリスク           | 「本丸はXだ」→「Xが最重要ターゲット」                  |
| データから読み取った解釈を勝手に書く           | ユーザーの結論を先取り       | 「このパターンから〜が一貫して効果的」                 |
| 施策を勝手に分類する                           | ユーザーの分類と異なる可能性 | 「機能リリース」を「パワーユーザー向け施策」と分類     |
| テンプレートの空欄をそれっぽく埋める           | 後から修正コスト発生         | リスクを勝手に想像して記載                             |
| データとユーザーの主張が違う時に黙って修正する | ユーザーの意図を無視         | 「一番増えた」を勝手に削除/変更                        |
| 「〜と考えられます」で推測を紛れ込ませる       | 推測を事実に見せている       | 「通知数と効果の相関から、通知効率が重要と考えられる」 |

## よくある失敗パターン

### 「読み取れること」セクションを勝手に追加する

データ表の後に「読み取れること」「ポイント」等の解釈セクションを追加しがち。
データは表で自明なので、解釈はユーザーに委ねる。解釈を入れたい場合は
「こういう読みであってますか？」と会話で確認してから書く。

### 施策の効果を「大きい/小さい」と評価する

「最大の効果を記録」「控えめなインパクト」等の評価は、ユーザーが言っていなければ
書かない。数字を並べれば読み手が判断できる。

### 比較表に「共通パターン」を追加する

施策比較表を作った後、「3施策に共通するパターン」等の分析を追加しがち。
ユーザーが「パターンを整理して」と言っていない限り、表だけで十分。
