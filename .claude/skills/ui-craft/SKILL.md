# UI Craft

AI がゼロから UI を作ると、訓練データで最も多いパターンに寄って「どこかで見た画面」になる。そのうえ、描画結果を見ずにコードだけで完了とするため、崩れや冗長さが残る。

このスキルは 2 つの手段でこれを防ぐ。1 つは、既存のデザインシステムと参照実装を出発点にして、判断の余地を減らすこと。もう 1 つは、実際に描画した画面を見て直すループを、完了の条件にすること。

## 判断の優先順位

規則どうしがぶつかったら、上にあるものを優先する。

1. **ユーザーが明示した指示と参照**：既存のデザインシステムから外れるなら、外れる点を伝えたうえで指示に従う
2. **プロジェクトの既存デザインシステムと既存コンポーネント**：利用者は既存の画面との一貫性で操作を学ぶため、単体で見て良い見た目より、隣の画面と揃っていることを優先する
3. **このスキルの原則**（下の「中心の原則」）
4. **`references/anti-patterns.md` の既定値**：既存の基準が無いときだけ使う出発点で、既存の値を上書きする根拠にはしない

WCAG 2.2 のレベル AA は、この順位に関係なく満たす。既存の値やコンポーネントが満たさないなら、既存の側を直す。references に添えた達成基準番号は、該当する基準を探す手がかりで、優先される範囲を限るものではない。見た目の判断で満たさなくなるなら、見た目の側を変える。

## 中心の原則

- **中身から組む**：実際に入るデータと文言を先に決めてから配置する。ダミーの短い文言で組んだ画面は、本物の長さが入った瞬間に崩れる
- **レイアウトに説明させる**：意味は位置・グルーピング・順序・大きさで伝え、文字のラベルや説明文は消すと意味を取り違えるものだけ残す。ただし入力欄の見えるラベルや取り消せない操作の説明など、`references/anti-patterns.md` の「ラベル・説明文」に挙げた例外は、この原則で消す対象にしない（ユーザーが明示して消すよう指示した場合は、上の優先順位に従う）。見た目で表した構造は、見出し要素やリストなどのマークアップでも表す。画面を読み上げで使う人には配置が見えないため
- **最も強い強調は 1 画面に 1 つ**：すべてを目立たせると、どれも目立たない。最も目立たせる要素を 1 つ決め、残りはそれより弱くする
- **装飾は役割があるときだけ**：影・グラデーション・アニメーションは、階層や状態の変化を伝えるために使う。「寂しいから足す」装飾が AI 感の主な出どころになる
- **描画して確かめるまで完了にしない**：コードの上では正しく見えても、画面では詰まり・はみ出し・揃いのずれが起きる

## 作業の流れ

### 1. 理解する

- 何を作るか（部品 / 画面 / 画面の一部）と、使う人がその画面で達成したいこと
- 誰が使うかと、製品のトーン（業務向けで落ち着いた、個人向けで親しみやすい、など）。既存のデザインシステムが無いとき、色・文字・余白の方向はここから決まる
- 既存のデザイントークン（色・余白・角丸・文字サイズの変数）、既存コンポーネント、近い既存画面。まずこれを探し、あれば従う
- 技術スタック（フレームワーク、CSS の書き方）と、描画して確かめる手段（開発サーバー、コンポーネントのプレビュー、スクリーンショットを撮るブラウザ自動化）

### 2. 中身を決める

- 表示する項目を、利用者にとっての重要度順に並べる。並べられないなら、画面の目的がまだ曖昧なので 1 に戻る
- 実データに近いサンプルを用意する。最長の名前・タイトル、0 件・1 件・大量件数、大きな数値と負の数、画像が無い場合、エラー時の文言を含める
- 各項目について、文字で書くか、配置や形で伝えるかを決める

### 3. 参照を選ぶ

ゼロから書かない。次の順で出発点を探す。

1. プロジェクト内の既存コンポーネントと近い画面
2. プロジェクトが使っている UI ライブラリの該当コンポーネント
3. `references/component-libraries.md` のカタログ

参照はそのまま貼らず、手順 1 で見つけたトークンと既存画面の書き方に合わせる。

### 4. 実装する

- 値はデザイントークンから取る。新しい値が必要なら、その場に直書きせずトークンとして定義する
- 見た目の違いは variant や size のような引数で切り替えられるようにし、呼び出し側でスタイルを上書きさせない
- hover・focus・active・disabled・loading・empty・error の状態を、最初から実装に含める。後から足すと、状態ごとに見た目がばらつく
- 迷ったら `references/anti-patterns.md` の該当カテゴリを読む

### 5. 仕上げる（描画 → 検査 → 修正のループ）

品質を最も左右する工程。`references/finishing.md` の検査を順に当て、直すものが無くなるまで「描画する → 検査する → 直す」を繰り返す。描画する条件の組み合わせ、検査の順番、意図を知らない読み手による確認の手順は、すべて `references/finishing.md` にある。

変更前の画面があるなら、変更前と変更後を同じ条件で並べて比べ、良くなったことを確かめる。

#### 変更の規模に合わせる

検査の範囲は、変更が影響する範囲に合わせて決める。

| 変更の規模                                     | 行う検査                                                                 |
| ---------------------------------------------- | ------------------------------------------------------------------------ |
| 文言・ラベルの追加や変更だけ                   | 引き算・描画条件・アクセシビリティの検査（`finishing.md` の 2・4・5）。変えた文言が loading・empty・error などの特定の状態でだけ出るなら、その状態を 6 の手順で表示してから 4 の条件で描画する |
| 1 つの部品の見た目                             | その部品を単体で描画し、`finishing.md` の 2〜6 を行う                    |
| 画面のレイアウトや情報の階層が変わる           | `finishing.md` の検査をすべて行う                                        |

複数に当てはまるなら、範囲の広い行に従う。

#### 描画できない環境

ブラウザ自動化が無い、ネイティブアプリでビルドできないなど、描画して見られない環境では、確かめられた範囲だけを報告する。描画しないまま「完了」とは報告しない。代わりに、トークンの値から計算したコントラスト比や、マークアップの構造のように、コードから確かめられることは確かめる。そのうえで、行えなかった検査を列挙し、作業を「未検証」として報告する。

## 完了の条件

規模に応じて行うと決めた `references/finishing.md` の検査と、変更前の画面があるときの変更前後の比較をすべて行え、直すものが残っていないときだけ「完了」と報告する。1 つでも行えなかった検査があれば、その一覧を添えて「未検証」と報告する。
