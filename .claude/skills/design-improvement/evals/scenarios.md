# design-improvement eval シナリオ

回し方は [`README.md`](./README.md)。

### S1: 式が同じでも別のルール（`fixtures/orders.ts`）

題材には、同じ計算式の重複、実装が 1 つしかない Strategy と Factory、boolean 引数があり、`checkout` と `canShip` が同じ条件式を持つ。この 2 つは「金額を確定できるか」と「発送できるか」という別のルールである。

**pass 基準**:

- 税込合計の重複を 1 か所にまとめ、Strategy と Factory を消す
- `checkout` の可否判定を `canShip` で置き換えない。別の名前のルールとして持つか、置き換えた場合は読み手が「確定と発送の関係」で詰まっていないことを読み手テストで示す
- `checkout` や `estimateTotal` の名前と動作のずれを、改名するか、残った誤読として報告の先頭近くに置く
- `checkout(id, true)` の boolean 引数を、呼び出し側で意味が読める形に変えるか、残した理由を報告する
- モジュールの外から観測できる挙動（DB に保存する値、送るメールの宛先と本文）を変えない
- 関数名や引数の形を変えた場合は、同じリポジトリ内の呼び出し側を書き換える前提で扱い、互換のための別名を残さない。題材の外から呼ばれていると判断して別名を残すなら、その判断の根拠を報告に書く
- 読み手テストを改善前と改善後で別の読み手に行い、改善後の読み手に誤読が残っていない

### S2: 誤った抽象と、触らなくてよいコード（`fixtures/members.ts`）

題材には、文字列の `type` で無関係な 3 処理を振り分ける `process`、意味の無い引数名 `flag2`、マジックナンバーの退会ステータス、本体が同じ 2 つの入力チェック、数行で完結する `isWeekend` がある。

**pass 基準**:

- `process` を処理ごとの関数に分ける
- 2 つの入力チェックの上限値を、別々に変わりうるルールとして扱う（1 つの共有定数のままにしない）
- `isWeekend` を定数化・設定化・クラス化しない
- 読み手テストを改善前と改善後で別の読み手に行い、改善後の読み手に誤読が残っていない
