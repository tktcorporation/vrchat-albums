# 設計改善：初見の読み手が意味を正しく推測できるコードにする

このスキルで設計を直すときは、次の 3 つの方針に従う。

- **基準は初見の読み手**：コードベースを何も知らない人が、コードを読んで意味を正しく推測でき、読みにくいと感じなければよい。KISS や SSOT などの設計原則は、この基準を満たすための道具として使う。読みやすくなったかは自分で判定せず、作業の経緯を知らない新しいサブエージェントに初見の人の代わりとして読ませて確かめる
- **まとめるかは変わる理由で決める**：2 か所が同じ式でも、変わる理由が別なら別のルールとして残す。抽象は、名前を読めば中身を開かずに済むときだけ置く
- **外部境界の挙動は保ち、内側は組み替える**：利用者や外部システムから見える挙動は変えない。その内側にある関数・引数・型・モジュールの形は、互換のための別名を残さずに組み替えてよい

この文書で「読み手」と書くときは、この確認に使うサブエージェントを指す。設計原則に照らして気になる箇所があっても、読み手が正しく読めているなら直さない。

## 手順

1. **測る**：読み手に対象コードを読ませ、誤読と詰まりを集める
2. **診断する**：誤読と詰まりのそれぞれについて、どの設計原則が崩れているかを特定する
3. **直す**：判断に迷う場面は「直す」の節の基準で決める
4. **測り直す**：「測る」で使っていない新しい読み手に改善後のコードを読ませ、誤読が残っていないかを確かめる
5. **報告する**：残った誤読と詰まり、直したものを報告する

書いた本人は意図を知っているので、名前と中身のずれに自分では気づけない。「測り直す」を省いて、読みやすくなったと自分で判定しない（省いてよいのは「測る」の節に書いた小さな規模のときだけ）。

読み手の回答と突き合わせる意図は、依頼、仕様、呼び出し元での使われ方から決める。他人が書いたコードで意図を決めきれない箇所は、推測で埋めずに依頼者に確認する。

## 測る：読み手テスト

この会話の文脈を持たない新しいサブエージェントを、読み手として起動する。渡すのは対象のコードファイルだけにし、設計メモ、診断結果、会話の経緯、このスキルは渡さない。対象が複数ファイルにまたがるときは、改善する範囲のファイルをすべて渡す。呼び出し箇所の読みやすさ（`send(id, true)` の `true` の意味など）を測るときは、呼び出し側のファイルも渡す。

質問は毎回次のものを使う。

```text
あなたはこのコードベースについて何も知らない評価者です。<対象ファイル> だけを読んでください。
推測で構いませんが、各回答に確信度（高/中/低）を付けてください。
1. このモジュールは何をするものか（2 文）
2. 公開されている各関数・型・定数が何を意味し、どんな場面で使われると思うか
3. 主要な関数を呼ぶと何が起き、どんなときに失敗や空振りになるか
4. 読んでいて引っかかった箇所、意味を推測しきれなかった箇所を、該当行の引用付きで全部挙げる（無理に作らない）
5. 名前とやっていることが食い違っていると感じた箇所
```

読み手の回答を自分の意図と突き合わせ、ずれを 3 種類に分ける。

| 種類 | 定義 | 例 |
| --- | --- | --- |
| **誤読** | 読み手が推測した意味が、意図と違う | `estimateTotal` を概算と読んだが、実際は確定額を返す |
| **詰まり** | 意味は合っているが確信度が中か低、または推測しきれない | 2 つの上限値がどちらも 50 で、同じルールかどうか分からない |
| **外部依存** | 渡したファイルの外を見ないと判断できない | `db.query` が 1 行を返すか配列を返すか分からない |

誤読と詰まりは直す。外部から見た挙動を変えないと解消できないもの（非推奨の別名でも解消できない、外部境界の名前による誤読など）だけは、残して報告する。外部依存は渡したファイルの読みやすさの問題ではないので、型や名前で補えるときだけ補う。

数行の関数 1 つを直すときのように、自分で読む方が早い規模では、「測る」と「測り直す」の両方を省いてよい。省いたことは報告に書く。サブエージェントを起動できない環境では、自分で読んだ結果を読み手テストの代わりにせず、読み手テストを行わなかったことと上の質問文を報告に書き、確かめ方を依頼者に委ねる。

## 診断する：誤読と詰まりを設計原則に結びつける

誤読と詰まりの多くは、次のどれかの設計原則が崩れていることで説明できる。「確かめ方」の問いは、崩れているかを見た目ではなく意味で判定するために使う。

| 設計原則 | 読み手に起きること | 確かめ方 |
| --- | --- | --- |
| **命名** | 名前から想像した動作と、実際の動作が違う。または名前から何も想像できない（`process`、`data`、`flag2`） | 名前だけを見て、中身を正しく言い当てられるか |
| **呼び出し側の読みやすさ** | 呼び出し箇所だけを見ても、引数の意味が分からない | 呼び出しの 1 行だけを見て、何が起きるかを言い当てられるか |
| **SSOT** | 同じルールが複数箇所にあり、どちらが正しいか、違いがあるかを探すことになる | 片方の仕様が変わったとき、もう片方も必ず同じく変わるか |
| **責務分離** | 1 つの関数やモジュールが無関係な仕事を抱え、どこまでが一続きの話か分からない | そのまとまりが変わる理由を 1 文で言えるか |
| **KISS** | 実装が 1 つしかないインターフェースや、中身を素通しするだけのラッパーを、読み手が開いて確かめることになる | その間接層を消すと、読み手が知るべき情報が失われるか |
| **抽象化の水準** | 1 つの関数の中で業務の流れと文字列の組み立てが混ざり、全体の流れを追えない | 関数本体を、同じ粒度の手順を並べた文章として読めるか |
| **知識の置き場所** | ルールがコメント、ドキュメント、呼び出し側の条件式にしか無く、コードの構造から読み取れない | そのルールを、コードの 1 か所で指し示せるか |

知識の置き場所が崩れていて、状態を型で表す、ルールを宣言として持つ、モジュールを概念で切る、といった手法が要るときは [references/domain-modeling.md](references/domain-modeling.md) を読む。

### 直さない場面

次の場面では何も変えない。

- 読み手に誤読も詰まりも無い。設計原則に照らして気になる箇所があっても直さない
- 数行で完結する単純な関数（`isWeekend` のようなもの）。定数化、設定化、クラス化をすると、読み手の負担が増えるだけになる
- 概念がまだ固まっていない。同じ概念を指す名前がコードや依頼の中で揺れているうちは、早く境界を引くと誤った境界を跨ぐコストを払い続けることになる

迷ったら、条件式や数値に名前を付けるだけで止める。型やモジュールを作らなくても、名前を付けるだけで詰まりが消えることは多い。

## 直す：判断に迷う 4 つの場面

判断に迷いやすいのは、重複をまとめるか、抽象を置くか、どこまで組み替えるか、名前が中身と合わないとき、の 4 つである。どの判断も、読み手の誤読や詰まりが出た箇所に対して行う。

### 重複をまとめるか：式の一致ではなく、変わる理由の一致で決める

2 か所が同じ式でも、それぞれが表すルールが別ならまとめない。まとめると片方の仕様変更がもう片方を巻き込むうえ、読み手には「なぜこの判定をここで使うのか」が分からなくなる。分けた側の定義には、別にしている理由を 1 文書く。理由が無いと、同じ中身の関数が 2 つ並んでいる理由を読み手が推測できず、次の改善でまたまとめられてしまう。

```ts
// まとめすぎ：確定処理の可否を「発送できるか」で判定している。
// 読み手は、確定と発送がどう関係するのかを推測できない。
if (!canShip(order)) return { ok: false };

// 別のルールとして分け、新しく分けた canConfirmTotal の定義に、分けた理由を書く。
function canShip(order: Order): boolean {
  return order.isPaid && !order.isShipped && !order.isCancelled;
}

/**
 * 合計金額を確定できるか。今は canShip と同じ条件だが、発送には在庫や配送先の条件が
 * 加わりうるのに対し、金額の確定は支払いの状態だけで決まるので分けている。
 */
function canConfirmTotal(order: Order): boolean {
  return order.isPaid && !order.isShipped && !order.isCancelled;
}
```

逆に、片方が変わればもう片方も必ず変わると言える関係なら、見た目が違っていても今すぐ 1 か所に寄せる。たとえば、同じルールを条件式でも、優先順位つきの if の並びでも持っている場合が当たる。そう言い切れず、共通部分に名前も付けられないときは、次の節の「待つ」に従う。

値が偶然同じ定数も、同じ考え方で扱う。ユーザー名と会社名の上限がどちらも 50 文字でも、別々に変わりうるなら定数を分ける。

### 抽象を置くか：読み手が中身を開かずに済むときだけ置く

抽象（関数、型、モジュールへの切り出し）を置いてよいのは、その名前を読めば、中身を開かずに呼び出し側を読めるときである。名前から中身を推測できない抽象は、読み手に中身を開かせるので、置かない方が読みやすい。

- **置く**：名前だけで意味が伝わり、呼び出し側の流れが短く読めるようになる切り出し
- **消す**：実装が 1 つだけのインターフェースとファクトリ、「将来の差し替え用」の拡張点、引数を素通しするだけのラッパー
- **待つ**：似た処理が 2 か所にあるが、同じ理由で変わるとは言い切れず、共通部分に名前も付けられないとき。3 か所目が現れて、共通の概念に名前が付くまで重複のままにする

文字列の `type` で無関係な処理を振り分ける汎用関数は、誤った抽象の典型である。呼び出し側からは何が起きるか読めないので、処理ごとの関数に分ける。

### どこまで組み替えるか：外部境界の挙動は保ち、内側は積極的に組み替える

保つのは、システムの外から観測できる挙動である。利用者に見える画面と出力、外部から呼ばれる API の契約、保存されるデータ（形と値の両方）、メールや外部連携への送信がこれに当たる。ここを変えると、コードを読む人とは別の、利用者や他システムに影響が出る。画面、HTTP API、DB のように外から観測される面は、同じリポジトリの中から使われていても境界として扱う。

境界より内側にある関数の分割、引数の形、内部の型、モジュールの切り方は、読みやすさのために積極的に組み替えてよい。呼び出し側は同じ変更の中で書き換え、互換のための別名やラッパーは残さない。残すと、読み手は新旧どちらを使うべきかを推測することになる。

関数やモジュールが外部境界かどうかは、呼び出し元を検索して決める。文字列や設定ファイルで名前を参照している箇所も検索に含める。同じリポジトリの中からしか呼ばれていなければ内側、別のリポジトリや外部のクライアントから呼ばれていれば境界として扱う。同じリポジトリ内でも、別のパッケージとして公開・リリースされているものは境界として扱う。

外部の挙動が変わっていないことは、境界を通すテスト（E2E テストや、公開 API を呼ぶテスト）で確かめる。組み替える前にそのテストが通ることを確認し、無ければ設計改善の一部として先に書く。テストを書くのが改善そのものより大きな作業になるときは、組み替える範囲を既存のテストで守れる部分に絞るか、依頼者に相談する。

組み替えの途中で見つけた不具合や仕様の曖昧さのうち、直すと外部から見た挙動が変わるものは、設計改善に混ぜずに報告へ回す。依頼の時点で挙動の変更も頼まれている場合だけ、あわせて直してよい。

### 名前が中身と合わないとき：名前を直す

名前のずれは、読み手が誤読する最も大きな原因になる。内側の名前なら、呼び出し側ごと改名し、旧名は残さない。旧名を残すのは外部境界の名前だけで、外部の利用者を壊さないよう次の順に対応する。

1. 中身に合った名前を新しく作り、旧名は非推奨の別名として残す
2. それもできないなら、残った誤読として報告の先頭に置き、改名した場合の影響範囲を添える

## 測り直す

改善後のコードを、「測る」で使っていない新しい読み手に読ませる。同じ読み手を使い回すと、前の版の記憶で読んでしまう。1 回のテストで使う読み手は 1 人でよく、読み手による揺れは次の回の新しい読み手で確かめる。

- 誤読が無くなり、残った詰まりのすべてに残す理由を書ける状態になるまで、「診断する」から「測り直す」までを繰り返す。最後の読み手テストは、最後の変更の後に行う。テストの後に足した修正は、小さくても確かめていない変更になる
- 3 回測り直しても誤読が残るときは、繰り返しを止める。同じ箇所で消えないなら、名前ではなくその箇所が表す概念そのものが曖昧な可能性が高い。毎回違う箇所に出るなら、改善の範囲が広すぎる可能性がある。残った誤読と考えられる原因を依頼者に示して、方針を相談する
- 改善で新しい詰まりが生まれていないかを見る。足した抽象や定数が、読み手の「引っかかった箇所」に挙がっていたら、その変更は戻す。その変更で解消した誤読があるなら、戻すのではなく、誤読も詰まりも生まない別の形を探す

## 報告する

報告は次の順に書く。

1. **残った誤読と詰まり**：誤読を詰まりより先に、同じ種類の中では多くの箇所から使われる名前ほど先に並べる。それぞれに、直せなかった理由と、直すために必要な判断を添える
2. **直したもの**：それぞれが、どの誤読や詰まりに対応したかを添える
3. **外部から見た挙動が変わる変更**：依頼の時点で挙動の変更も頼まれていた場合にだけ、何がどう変わるかを書く。頼まれていなければ、この欄は「無し」になる
4. **見つけたが直さなかったもの**：直すと外部から見た挙動が変わる不具合や、仕様の曖昧さ

読み手テストを省いた場合は、そのことと理由も書く。

## 実現手段はプロジェクトの規約に従う

網羅的な分岐、境界での型変換、同じ型の値を取り違えないための専用の型、依存の注入といった道具は、言語とライブラリで変わる。プロジェクトのコード規約に定めがあればそれに従い、無ければ既存コードで多数派の手段に合わせる。
