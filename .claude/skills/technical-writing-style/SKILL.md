# 日本語技術文書の文章規範点検

PRD/設計doc/Wiki記事/レポート/PR本文/Issueなど、対外的な日本語技術文書を執筆/推敲するときに、以下の規範に従って書く/点検する。

## 何のためのスキルか(位置づけ)

- `faithful-doc-writing` … 内容の忠実性(言ってないことを勝手に足さない)
- `prd-review` … PRD特有の8観点(ロジックの一貫性/仮説の明確さ等)
- `pr-first-reader-check` … PR限定/初見の読み手に文脈と可読性が伝わるか
- **本スキル** … 上記のどれでもカバーしない、文〜文書全体の文章作法(段落構成/論証の厳密さ/読み手の負荷管理/LLM口調/冗長排除/見出し/読者への誠実さ)。対象はPRDに限らずWiki記事/レポート/PR本文/Issue全般

内輪語禁止/技術説明の正確性は `@.claude/rules/agent-work-discipline.md`、結論だけを書く原則は `@.claude/rules/conclusion-only-output.md` が別途カバーする。本スキルではそれらと重複する項目は本文を書かず参照だけにする。

## いつ使うか

- PRD/設計doc/Wiki記事/レポート/PR本文/Issueを新規に書くとき(執筆規範として)
- 書き上げた原稿を推敲するとき(点検チェックリストとして)
- 「LLMっぽい」「まどろっこしい」「読みにくい」と感じたとき

## 検査対象(すべて見る)

対象ドキュメントの本文全体。見出し/段落/箇条書き/強調/語彙選択のすべてを見る。コード片やログ/設定ファイルの引用部分は対象外。

## 整形

- 一文ごとに改行する。段落の区切りは空行で示す。
- コード/差分/ログ/設定ファイルの断片はコードブロックで示す。
- 用語を本文中で初めて定義/導入するときは太字にする。すでに導入した語を話題として指すときは「」を使う(初出の定義は太字、以後の言及は「」)。本筋から一段外れる補足は本文に並べず脚注に降ろす。
- ダッシュ(em ダッシュ「—」、horizontal bar「―」、二倍ダッシュ「——」)を地の文/見出し/箇条書きのラベルと内容の区切りに使わない。同格/補足の挿入は括弧に、言い換え/敷衍は句点で二文に分けるか読点でつなぐ。ラベルと内容の区切りは後述の全角コロンにする。範囲を示す en ダッシュ「–」やコードブロック/書誌情報は対象外。
- 中黒(・)を並列で使わない。単一の固有名詞の内部では使ってよい。
- 見出しに区切り線(「種別──主題」のような二要素の詰め込み)を使わない。見出しは単一の自然な句にする。
- 用語とその定義を並べる箇条書きは全角コロンで「**用語**：説明」と書く。

## 段落と論証の構成

段落は論証の一歩であり、読み手は段落単位で論理を追えなければならない。

- 一つの段落には一つのトピックだけを置く。場面が複数混ざった長い段落は、一歩ずつの段落に分割する。
- 段落の最初の文を読めば、その段落が何の話かわかるようにする。
- 段落の先頭では、前の段落との論理関係を接続表現で明示する(「であれば」「実際」「しかし」)。
- 新しい概念/用語を導入するときは、いきなり「XはYである」の辞書型断定で始めない。先に対象を置き、次に働き/差分を述べ、必要なら三文目で定義を与える。
- 論証は一方向に進める。結論を出してから反論を処理し、また結論を言い直す構成にしない。反論/疑念の処理を終えてから、結論を一度だけ置く。
- 読み手が立てそうな誤った解釈は、明示的に否定してから本当の理由を述べる(「その理由は『〜だから』ではない。〜だからだ」)。
- 「AではなくB」と否定するときは、否定の根拠を一文添える。
- 何かを否定/限定するときは、否定する命題そのものを「」で正確に書き出す。「何もかもが解決するわけではない」のような漠然とした否定で済ませない。

## 論証の厳密さ

書き上げたら、読み手の反論を先回りして次を点検する。

- 推量/可能性を表す語(「かもしれない」「だろう」)を、根拠なく主張を弱めている場合だけ削る。事実未確認の可能性、読み手が抱きそうな疑念、反実仮想を表す場合は不確実性を保つ。断定に直せるのは、本文内の根拠で命題が確定している場合に限る。
- 異なるものを「同じ」とまとめない。区別すべき対象(別々の原因、種類の違う問題)を一括りの言葉でくくらない。
- 複数の要因がある事象を、単一の原因に還元しない。それぞれを切り分け、どれがどれを説明するのかを対応づける。
- 同じ概念の扱いを文書内で一致させる。ある節で立てた分類/定義を、別の節で変えない。
- 因果を主張するときは、その機構(なぜそうなるのか)を一文で示す。「AだとBになる」とだけ書いて理由を省略しない。
- 検出/保証/解決を「必ず」できるかのように書かない。条件付きで正確に述べる(「〜しやすい」「〜できることが多い」)。
- 挙げた例が主張の全体を実際に支えているかを確認する。例が主張の一部しか支えないなら、主張の範囲を例に合わせて狭める。
- 「後で扱う」と前方に逃がした論点は、本当にそこで回収されることを確認する。

## 読み手の負荷の管理

読み手の記憶と注意は有限の資源として扱う。

- 後で参照する必要のない固有名(ファイル名/関数名/識別子)を出さない。一般的な言い方で済ませる。
- 抽象的な言い回しの指す内容が文脈から一意に決まらないときは、丸括弧による同格挿入でその場で特定し、読み手に前を読み返させない。
- 新しい例を追加して読み手が保持すべき文脈が増えるときは、前の例と何が違うのか、なぜもう一つ必要なのかを前置きする。
- 冒頭や導入では、これから扱う内容に関係しない過剰な詳細を詰め込まない。議論に必要な具体は残す。省略の典型は、装飾的な精度(時刻/HTTPステータス/カバレッジ率など)や、後で参照しない固有名。

## 視点と語り

- 結果の羅列や受動態(「特定され、判明した」)ではなく、行為者を主語にした動作の連なり(「調査して特定し、見つけた」)で書く。
- 対象を指す語は具体的に選ぶ。「AI」「ツール」のような広い語でぼかさない。
- 用語/術語を導入したら、以後はその語で通す。曖昧な言い換えに後退しない。
- 術語/訳語は、その分野で慣用されている語を選ぶ。意味の近い語を一般語の感覚で充てない。
- 読み手の呼称/二人称の使い方は `@.claude/rules/agent-work-discipline.md` の内輪語禁止と同じ目線で扱う(役割名で書き、暗黙の前提を共有させない)。

## 演出の抑制

演出は全面禁止ではなく、節度の規範である。修辞は、それが効果を生む箇所でのみ使う。

- 溜め(「ここには〜が潜んでいる」)や修辞疑問で導出を演出するのは、緊張が議論に効く要所に限る。説明で足りる箇所では、そのまま述べる。
- 短い決め台詞を独立した段落にして緊張を作る演出を多用しない。
- 太字強調を多用しない。誤読を防ぐ否定や結論など、論理の要所に限り使う。
- 「〜してはならない」という命令調の断定より、判断として書く形を選ぶ。
- 転回点を過剰に劇的にしない。事実を述べる一文で足りる場合が多い。
- 帰結の列挙によって危険や事故を煽らない。
- 「重要なのは〜である」のような前置きで主張を予告しない。主張をそのまま書く。
- 「AではなくBだった」という対句の決め台詞を多用しない。

## LLM っぽい表現の禁止

LLMが大量生成する、中身のない型に誘惑されない。書き上げたら、この節で点検する。

次のような言い回しは、論点を増やさず「ちゃんと書いている感」だけを付ける。使わない。

- **予告と総括**：「重要なのは〜である」「本文書では〜を扱う/探求する」「ここでは〜について見ていく」「まとめると」「要するに」(直前の言い換えだけのとき)、「〜に他ならない」
- **正面から系**：「正面から扱う」「正面から回収する」「正面から見る/書く/立てる」という言い方は、中身の代わりに姿勢だけを宣言する
- **空虚な形容**：「不可欠」「核心的」「鍵となる」「根本的な」(主張の中身を説明せず強調だけする)、「多角的」「包括的」「総合的」(何をどう見たかを書かない)
- **空虚な動詞**：「掘り下げる」「深掘りする」「言語化する」(何をどう書いたかを示さず終わる)、「触れる」「言及する」(一段落で済ませるだけ)
- **接続の型**：「〜において」「〜という側面から」「〜の観点から」(新情報なし)、「さらに」「また」「加えて」の連打
- **弱い緩和と称賛**：「〜と言えるだろう」「〜かもしれない」(根拠なく主張を弱める場合だけ。推量/仮定/読み手の疑念なら残す)、「非常に」「極めて」「大いに」(中身のない強調)

## 冗長の排除

無駄な文章をなるべく残さない。

- 同じ主張の繰り返しと、隣接する節の役割重複は `@.claude/rules/conclusion-only-output.md` の「過程/対比/自己言及を書かない」と同じ目線で扱う(一つの主張は一度だけ書く)。
- 場面を描写した直後に、その内容を要約し直さない。意味づけの一文だけを置く。
- 同じ論理的役割を持つ並列の事実は、文を分けて重ねず一文にまとめる。
- 読み手が自力で補える中間段階の説明は書かない。
- 一つの主張を数文かけて述べているなら、一文にまとめる。主張が複数あるなら、まとめずに文を分けたまま残す。
- 圧縮するのは議論であって、書き方ではない。文を断片や省略記法、記号による連結(矢印の連鎖、ラベルの積み上げ)へ潰すと、語数は減る一方で、関係を補う負荷が読み手へ移る。短さと分かりやすさが衝突したら、分かりやすさを取る。
- 接続や評価のためだけの文(「それ自体はよいことである」など)を置かない。
- 想像上の読み手との問答(問いを立てて一語で答える形)を修辞として使わない。主張はそのまま述べる。
- ためらいのある弱い述語(「有効な対策であり」など)で済ませない。本文内の根拠で確定していることは強く具体的に言い切る。ただし不確実性/可能性/仮定を表すための弱い述語は保持する。

## 見出しの付け方

見出しは内容を特定できる具体的なものにする。その節が答える問い、または扱う対象を指す句にする。

- 作業の手順だけを述べる見出し(「例に戻す」等)や、情報量のない見出しにしない。
- 見出しを、節の結論を言い切る「セリフ」にしない。見出しの時点で読み手がオチを知る状態を避ける。
- 節で扱っている対象を指す名詞句でもよい。疑問形か断定形かは、本文のトーンに合うほうを選ぶ。

## 読者への誠実さ

- 例が作為的に見えうる場合、それを隠さない。読み手の疑念を先回りして認め、現実に十分あり得ることの根拠を短く添える。
- その根拠は、著者の断定ではなく、読み手自身の経験に訴える一般的事実や通説に求める。
- 確認していないことを、確認したかのように滑らかに書かない。`@.claude/rules/agent-work-discipline.md` の「技術説明の正確性」(機構名を出すときは前提条件も書く、確認できないなら憶測と明示する)と同じ目線。

## 出力フォーマット

推敲チェックとして使うときは、次の表形式で指摘する。

```markdown
## 文章規範点検: [対象ドキュメント名]

### 判定: 【OK / 要修正 N件】

### 指摘

| 箇所    | 文言                   | カテゴリ | なぜ問題か                 | 直し方                                             |
| ------- | ---------------------- | -------- | -------------------------- | -------------------------------------------------- |
| 3段落目 | 「重要なのは〜である」 | LLM口調  | 予告だけで中身が無い       | 主張をそのまま書く                                 |
| 見出し2 | 「対応方針を決める」   | 見出し   | 手順だけで内容を特定しない | 「〜方針の決定基準」のように対象を特定する句にする |

### 直した結果(修正する場合)

- [箇所] before → after
```

新規執筆のガイドとして使うときは、上記カテゴリを執筆前に一通り目を通し、書き上げた後に同じ表で自己点検する。

## やりがちな失敗

| 失敗                                                       | どうするか                                                                                                             |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| LLM口調のリストだけ見て、論証の厳密さ/段落構成を素通しする | 全カテゴリを見る。LLM口調は一部でしかない                                                                              |
| 推量表現(「かもしれない」)を機械的に断定へ変える           | 不確実性/疑念/仮定を表す推量は残す。根拠なく弱めているものだけ削る                                                     |
| 「構造(見出し/表)が整っている=読みやすい」と判断する       | 見出し/表が良くても個々の文/段落が長ければ詰まる                                                                       |
| 内輪語禁止/結論だけ書くの指摘を本スキルでも重複して出す    | それらは `@.claude/rules/agent-work-discipline.md` / `@.claude/rules/conclusion-only-output.md` に譲り、参照だけにする |
| 指摘を出して直さない                                       | 執筆中の自己点検なら、その場で直してbefore→afterを示す                                                                 |
