# PR レビュー・修正ループ

PR作成前のローカルブランチ差分に対して、`pr-deep-review` のレビューと `upstream-fix` の根本原因修正を、指摘が収束するまで繰り返すスキル。1回のレビュー→修正では終わらせず、指摘が出なくなる(または直しても変わらなくなる)まで自動的にループする。

## 何のためのスキルか(位置づけ)

```
pr-deep-review          →  1回のレビューで4レンズの指摘を出す
upstream-fix             →  1件の修正依頼に対する根本原因分析(症状→直接原因→根本原因→A/B/C提案)
pr-review-loop(本スキル)  →  上記2つを「指摘全体」に対して収束するまで繰り返す
```

本スキルは `pr-deep-review` の手順そのものは変更しない。`upstream-fix` の Phase 1-4 の視点も変更しない。変えるのは適用範囲で、upstream-fix を**1件の指摘ではなくラウンドの指摘全体**に対して適用し、それを複数ラウンド繰り返す。

`.claude/rules/pr-self-review.md` が定める `gh pr create` 前のゲートは、本スキルのループを収束まで回すこと。収束条件の正確な中身（何ラウンド必要か、最後のラウンドに何を求めるか）はそちらの「仕組み」節を読む。ここでは手順だけを示す: ラウンドごとに `bun .claude/hooks/record-pr-review.ts <指摘件数> [codex]` で記録し、hook が収束を認めなければ Step 1 に戻る。

## いつ使うか

- PR を作る前の仕上げ。依頼が無くても、PR 作成に進む前に必ず回す
- 「収束するまでレビューと修正を繰り返して」「指摘がなくなるまで直して」といった明示的な依頼

**使わなくてよい場面**: 「深くレビューして」だけの依頼(`pr-deep-review` 単体で足りる)。1件だけの明確なバグ修正依頼(`upstream-fix` 単体で足りる)。

## 手順

### Step 0: スコープ確定

```bash
# origin/HEAD が未設定なら一度だけ: git remote set-head origin --auto
default_branch="$(git symbolic-ref --short refs/remotes/origin/HEAD | sed 's@^origin/@@')"
git fetch origin "$default_branch"
git status --porcelain
git diff "origin/$default_branch...HEAD" --stat
git diff "origin/$default_branch...HEAD"
```

`git status --porcelain` に出力があれば、レビュー対象に入っていない変更がある。コミットしてから続ける(まだ書きかけで残したい変更なら、その旨をユーザーに確認する)。以降のラウンドでも Step 5 の直後に必ずコミットするため、`git diff origin/<default-branch>...HEAD` は毎ラウンドその時点の全変更を指す。

前ラウンドの Step 3 クラスタ診断結果 = 空、として開始する。

### Step 1: レビュー(ラウンドごとに専用サブエージェント、または codex)

収束させる最後のラウンドにするなら codex review(下)、それ以外は `Agent` ツールでサブエージェントを起動する(こちらが基本)。

`Agent` ツールで、現在の差分を `pr-deep-review` の手順でレビューするサブエージェントを起動する。

```
Agent: "以下の差分を pr-deep-review スキル(.claude/skills/pr-deep-review/SKILL.md)の
手順でレビューせよ。差分: <git diff origin/<default-branch>...HEAD の内容>
狙い(基準線): <イシュー/PRの狙いが分かれば>

指摘を file / summary / severity(Critical/Important/Minor) / category
(spec-mismatch / correctness / code-quality / design-consistency) の
構造化リストで返せ。レビューの詳細な思考過程は返さず、指摘リストだけを返すこと。"
```

**codex review で行う場合**: `.claude/rules/codex-pairing.md` の手順で `codex review --base <default-branch>` を実行する(プロンプト末尾に、上記と同じ file/summary/severity/category の構造化リストで返すよう指示を添える)。出力を同じ形式の指摘リストとして Step 2 以降に渡す。`codex` が使えない環境では code-reviewer 系のサブエージェントで代える。

レビューの詳細はサブエージェント内に閉じ、メインセッションには指摘リストだけを持ち帰る。ラウンドを重ねてもメインのコンテキストは膨らまない。

### Step 2: 収束判定

- 今ラウンドの指摘が0件 → このラウンドが codex review なら `bun .claude/hooks/record-pr-review.ts 0 codex`、そうでなければ `bun .claude/hooks/record-pr-review.ts 0` で記録する。コマンドの「収束」は PR 作成前の条件を示す。既存 PR の外部指摘後は、指摘を観測した後だけで 2 ラウンド以上（最後は codex review）が揃ってから Step 7 へ進む。まだ 1 ラウンドなら Step 1 をもう一度行う。外部指摘がない場合は、コマンドの出力が「収束」なら Step 7 へ、「未収束」ならその出力が示す理由（ラウンド数不足・最後が codex でない、など）を解消する Step 1 をもう一度行う（正確な収束条件は `.claude/rules/pr-self-review.md` の「仕組み」節を参照）
- 今ラウンドの指摘が指し示す根本原因を、**前ラウンドの Step 3 で診断したクラスタ**と比較する(素の指摘リストの文字列同士を比較しない)。指し示す根本原因が前ラウンドから変わっていなければ**意味的に同じ**とみなす(文言の揺れは同一とみなす) → **途中収束**(直しても変わらない状態)。下記「非収束そのものを診断する」で全ラウンドを振り返り、レビューが続く原因と設計・要件・進め方を変える案を示してユーザーと方針を決める。残る指摘を受け入れる方針が選ばれた場合だけ、現在の HEAD に対して codex review をもう一度行い(この回も指摘は残るはずだが、それが受け入れ対象であることを確認する)、その実際の件数のまま `accepted` を付けて記録する(0 件だと偽らない)。別の方針が選ばれたら Step 3 へ。記録したら Step 7へ
- どちらでもなければ Step 3 へ

記録コマンドが「振り返りが必要」と言って記録を保留した場合(終了コード 1)は、収束でも未収束でもない。下記「振り返り」を行い、保留されたラウンドを同じ引数でもう一度記録する。

### Step 3: クラスタリング&診断(指摘"全体"に対して行う)

`upstream-fix` の Phase 1-3 の視点を、今ラウンドの指摘**全件**に横断的に適用する。1件ずつではなく、まとめて見る。

1. 各指摘の直接原因を洗い出す
2. 同じ設計上の原因(責務配置・データ正規化不足・契約の曖昧さ・抽象化不足)から出ている指摘をグループ化する
3. 「これを1箇所直せば複数の指摘がまとめて消えるのでは」を探す。他と関連しない指摘は無理にまとめず単独クラスタのままでよい
4. このラウンドのクラスタ診断結果は、次ラウンドの Step 2 の比較対象として保持しておく

### Step 4: 修正方針決定(クラスタごと)

`upstream-fix` の判断基準に従い、クラスタごとに A(フル改善)/B(上流修正)/C(局所修正)を選ぶ。

- デフォルトは **B(上流修正)**
- C(局所修正)は「同じ種類の問題が他に無い」と確認できた場合のみ許容する
- クラスタの規模が A 相当(既存コードの大きな再設計)まで見えたときは、黙って進めずユーザーに提案して確認してから着手する

### Step 5: 修正実行

**メインセッションで** Edit する(サブエージェントに丸投げしない。Step 3/4 の診断・判断根拠を保持したまま直す)。1クラスタ=1つの筋の通った変更として実装する。指摘ごとにバラバラに直さない。

直したらこのラウンドの修正をコミットする。Step 0 の差分は `origin/<default-branch>...HEAD` で取るので、未コミットの修正は次ラウンドのレビュー対象に入らない。

コミットはするが push はしない。push してよい作業なら、Step 7 のレポートを出した後に 1 回だけ行う。収束で終える場合も、ユーザーが打ち切りを選んだ場合も、push してよいかは依頼の範囲に従って判断する（`.claude/rules/ci-workflow.md` の「セルフレビューの往復では push をまとめる」はタイミングだけを定める）。GitHub 上のレビュー指摘を受けてこのループを回している間も、収束前に局所修正を push しない。未 push のコミットを促す hook やリマインダーがラウンドごとに届いても、それを理由に push しない。

### Step 6: ラウンド継続判定

このラウンドの指摘件数を `bun .claude/hooks/record-pr-review.ts <件数> [codex]` で記録する(指摘 0 件なら 0。codex review のラウンドは第 2 引数に `codex` を渡す)。

記録コマンドの出力が「振り返りが必要」と言ったら、Step 1 に戻る前に下記「振り返り」を行う。hook が一定ラウンドごとに強制し、済ませるまで、収束しないラウンドを記録できない。

- 続ける場合 → Step 1 へ戻る(Step 0 のコマンドで差分を再取得する。修正前の古い diff を使い回さない)
- 指摘が停滞したとき、またはレビューが `LONG_REVIEW_ROUNDS` に達したとき → 下記の振り返りで非収束の原因と設計案をまとめ、ユーザーと進む方向を決める

途中収束は Step 2 の中で処理する(上記参照)。自分の判断だけで 0 件や accepted にしない。

#### 振り返り(一定ラウンドごと。hook が強制する)

レビューが長引いていること自体が、構造を疑う十分な合図になる。指摘件数は確率的に減ることがあるので、件数が下がっていても、指摘の中身を見て「このまま進めてよいか」「もっと良い解決策はないか」を確認する。収束に向かっている実感の有無に関係なく、間隔ごとに必ず行う(間隔は `.claude/hooks/review-policy.ts` の `CHECKPOINT_INTERVAL`)。

1. 直近の指摘を、根本原因で分類する(何種類か、どの箇所・どの規則に集中しているか)
2. 同じ構造が原因で、同種の指摘が形を変えて出続けていないかを、下記「非収束そのものを診断する」の手順で確認する
3. 同じ責務・不変条件・変更箇所に指摘が集中していないか、修正のたびに分岐・状態・例外処理が増えていないかを確認する
4. 個々の症状を直し続ける以外に、発生源を一つの契約・型・実行境界へ閉じ込める方法や、規則を減らす・一本化する方法がないかを検討する
5. 結論を、次のとおり決めて記録する。診断メモには 1〜4 の検討結果を書く(文字数の下限は hook が検査する)

   ```bash
   bun .claude/hooks/record-pr-review.ts checkpoint <continue|replan|asked> "<診断メモ>"
   ```

   - `continue`: 分類の結果、共通の構造的原因は見つからず、今の方針で収束できると判断した
   - `replan`: 構造的原因や、より良い解決策を見つけたので、方針を変える
   - `asked`: 指摘が続く原因と設計・要件・進め方の案を示し、ユーザーと進む方向を決めた

指摘件数が最良値を更新していない停滞では、hook は `asked` 以外を受理しない。ブランチのラウンドが `LONG_REVIEW_ROUNDS` に達した後も、件数の傾向に関係なく `asked` が必要になる。どちらも「続けるか」だけを聞かず、非収束の原因を診断して設計・要件・進め方の案を比較し、採る方針をユーザーと決める。停滞していない定期的な振り返りでは、診断の結果に応じて `continue` または `replan` を記録できる。

**確認が必要なときは、レビューを続けるかだけを聞かない。** 先に全ラウンドの指摘を並べ直し、同じ原因から出たものをまとめる。各まとまりについて「守ろうとした要件・不変条件」「指摘が繰り返された直接原因」「局所修正で消えなかった理由」を示す。特に、同じ責務が複数箇所にある、修正のたびに分岐が増える、レビューごとに前提が変わる、要件が過剰、レビューの対象が広すぎる、といった**ループが続く仕組み**を特定する。指摘が分散しているなら、集中していない根拠と、作業の切り方や対象範囲に無理がないかを示す。

その診断から、実行可能な方針を少なくとも 2 案作る。各案に変更する責務・契約・要件、解消できる指摘、残るリスク、レビューと CI の追加コストを書く。推奨案と理由を添え、**どの設計方針を採るか**をユーザーに質問する。要件を緩める案や残る指摘を受け入れる案は、その影響を具体的に示す。回答が来るまでは、次の修正・レビュー・push・PR 作成へ進まない。回答後の `asked` メモには診断と選ばれた方針を記録し、その方針で実装とレビューを再開する。

決定の記録は自己申告で、hook はユーザーへ確認したかを検証できない。確認していないのに `asked` を記録することは、`agent-work-discipline.md` が禁じる虚偽の記録にあたる。

#### 非収束そのものを診断する

**考え方**: レビューを重ねても件数が0に減らない原因は、その領域のコードにバグが多いこと(実装密度)だけではない。設計の筋が悪く、1つの欠陥がラウンドごとに違う症状・違うファイルとして表れている場合がある。1つの不変条件を守る処理が複数箇所に個別実装され、直すたびに別の箇所の直し漏れが次のラウンドで見つかる場合もある。どちらも、指摘を1つずつ潰しても欠陥の発生源は減らないので収束しない。振り返りのときは、指摘を1件ずつ見るのをやめ、**指摘の集合そのもの**を診断する。

Step 2 の途中収束判定は「直前ラウンドと同じ根本原因が繰り返されているか」という**隣接ラウンド同士**の比較にとどまる。指摘の文言・根本原因がラウンドごとに違って見えても、指摘が出続けた事実は、`upstream-fix` の「収束しない指摘は、中身ではなく『形式』の欠陥」（Phase 2 の該当節）で診断できる。Step 3 のクラスタリングが 1 ラウンド分の指摘を対象にするのに対し、ここでは**全ラウンドの指摘を横断**して見る点が異なる。

1. 各ラウンドの Step 1 で持ち帰った指摘リストを、直したものも含めて並べる(記録に残るのは件数と前回までの振り返りの診断メモで、指摘そのものは残らない)
2. 各指摘が指すファイル・処理を見て、少数の箇所に集中していないか確認する(ファイル単位の粒度で十分。`git log --oneline origin/<default-branch>..HEAD -- <path>` で各ラウンドの修正コミットがどのファイルに触れているかを見ると、体感ではなく件数で確認できる)
3. 集中している場合、その箇所に共通する設計上の欠陥を `upstream-fix` の Phase 2〜3 の要領で特定する。典型は「同じ不変条件を守る処理が複数箇所に重複実装されている(呼ぶたびに1箇所ずつ直っては別の箇所で漏れが見つかる)」「不変条件を型やスキーマで保証しておらず、手続き的な手順の正しさに依存している」「守っている要件そのものが、実際の入力や利用規模に対して過剰に厳格」のいずれか
4. 特定できたら、それを解消する変更を Step 4 相当の方針として立てる。前 2 つの欠陥は重複の一本化・型による保証という**コード側の直し方**で解決するが、3 つ目(要件が過剰)は**要件そのものを緩めるトレードオフ**でしか解決しない。守ろうとしている要件が実態に対して重すぎると、コードを書き直しても同種の欠陥が形を変えて再発するためである。要件を緩めてよいかはユーザー判断なので、次の `AskUserQuestion` で選択肢として提示し、実装が決まってから着手する

指摘が特定の箇所に集中せず散らばっている場合は、設計の欠陥と決めつけない。対象範囲が広すぎる、レビュー観点が毎回変わる、独立した問題が多い、といった原因を確かめる。停滞時は `asked` でユーザーと方針を決める。

ユーザー確認が必要な場合は、上の診断と設計案から質問を作る。指摘推移(何件→何件)と診断結果は常に添える。「もう一度レビューするか」「続行するか」だけを選択肢にしない。

- 集中が見つかった場合: 発生源を一本化する案と要件・範囲を変える案などを、効果と影響で比較して相談する。停滞していない振り返りなら、依頼の範囲内で `replan` できる
- 集中なしの場合: 作業を分割する案と対象範囲を絞る案などを比較する。「集中なし」だけを伝えて続行可否を聞かない

### Step 7: レポート

収束した場合は、指摘の根本原因と確定した対応をまとめる。非収束で相談する場合は、ラウンドの時系列より先に**なぜレビューが続いているか**を原因別に示し、設計・要件・進め方の案と推奨理由を比較して方針を尋ねる。`.claude/rules/conclusion-only-output.md` に従い、試行錯誤の過程(捨てた案等)は書かず、判断に必要な事実と選択肢を書く。accepted で収束した場合・途中収束のまま止めた場合は、残る指摘をユーザー判断事項として明記する（PR 本文にも同じ内容を書く）。

判定が「準備完了」「準備完了(要受理事項の記載)」のときだけ、各ラウンドの記録（`bun .claude/hooks/record-pr-review.ts <指摘件数> [codex] [accepted]`）が済んでいれば `gh pr create` が通ることを伝える。「途中収束(要判断)」「中断(打ち切り)」のときは、まだ `gh pr create` が通らないこと、続行するには何が要るかを伝える。

## 出力フォーマット

判定ラベルは Step 2 / Step 6 の結果に対応する: 指摘0件で収束→準備完了、ユーザーが受け入れて accepted で収束→準備完了(要受理事項の記載)、ユーザーの受け入れを得られず未収束→途中収束(要判断)、ユーザーが確認で続行を選ばなかった→中断(打ち切り)。

```markdown
## PRレビュー・修正ループ: [対象ブランチ]

### 判定: 【準備完了 / 準備完了(要受理事項の記載) / 途中収束(要判断) / 中断(打ち切り)】

### 非収束の診断（相談が必要な場合）

| 指摘のまとまり | レビューが続く原因 | 方針案と影響 |
| ------------ | ------------------ | ------------ |
| [共通する指摘] | [局所修正で消えない理由] | [設計・要件・進め方の案] |

推奨案: [案と理由]。ユーザーに決めてほしい点: [採る設計・要件・進め方]。

### ラウンド別サマリ

| ラウンド | 指摘件数 | 見つけた根本原因     | 対応                |
| -------- | -------- | -------------------- | ------------------- |
| 1        | 3件      | [クラスタの根本原因] | [B: 上流修正の内容] |
| 2        | 0件      | -                    | 収束                |

### 残っている指摘(準備完了(要受理事項の記載)・途中収束(要判断)・中断(打ち切り)の場合)

[file / summary / なぜ直せなかったか]
```

## やりがちな失敗

| 失敗                                                                        | どうするか                                                                                                       |
| --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 指摘が出るたびにその指摘だけを消す最小パッチを逐次当てる                    | Step 3 のクラスタリングを飛ばした兆候。ラウンドの指摘全体を並べ直してから修正に入る                              |
| クラスタ診断でAが見えているのに確認なしでCに留める                          | upstream-fix と同じ理由でNG。A相当が見えたら黙って進めずユーザーに提案する                                       |
| 指摘セットの比較を文字列完全一致でやろうとする                              | 同じ根本原因を指していれば文言の揺れは同一とみなす。意味的に判断する                                             |
| 長引いても確認せず回し続ける、または黙って諦める                            | 振り返りのとおり `AskUserQuestion` で必ずユーザーに確認する                                                      |
| 振り返りのときに、指摘が特定箇所に集中していないか診断せずに続行/打ち切りだけ聞く | Step 6「非収束そのものを診断する」を飛ばした兆候。全ラウンドの指摘を横断して集中の有無を先に確認する |
| 件数が下がっているから、と指摘の中身を分類せずに振り返りを済ませる | 件数の減少は確率的にも起こる。指摘の根本原因と、別の解決策の有無を確認して診断メモに書く |
| 確認が必須なのにユーザーへ確認せず `asked` を記録する | 虚偽の記録。`AskUserQuestion` で答えを得てから記録する |
| レポートに各ラウンドの試行錯誤・捨てた修正案を書く                          | `conclusion-only-output.md` 違反。確定した対応だけを書く                                                         |

## 関連ルール

- `.claude/skills/pr-deep-review/SKILL.md`: 毎ラウンドのレビュー手順そのもの
- `.claude/skills/upstream-fix/SKILL.md`: クラスタごとの根本原因分析・修正方針決定
- `.claude/rules/conclusion-only-output.md`: レポートは結論だけを書く
- `.claude/rules/pr-self-review.md`: `gh pr create` 前のゲート。本スキルの各ラウンドを記録することで満たす
